# NFO 封面双版本导出方案

状态：已按方案实现并进行回归验证（2026-09-05）。下文保留研究时的现状与建议；实际行为见 [兼容性说明](NFO_COMPATIBILITY.md#封面导出更新2026-09-05)。实现时确认当前 Electron nativeImage 不能解码 WebP，相关封面会提前标记不可用；JPEG/PNG 双图导出、方向校正和裁剪已通过真实编解码验证，消费端双图显示尚未重新 smoke。

## 结论

建议将“影片封面”导出升级为按图片方向自动生成产物：横版封面保留完整横图，并生成真正的竖版 poster；竖版封面只导出 poster。NFO 的 poster 引用必须指向竖版产物。已有“详情背景”继续单独导出，不用整张横版封套代替。

首轮目标是修复外部软件的竖版海报展示，并保留横版封面的完整内容；不承诺所有客户端都提供横版封面入口。不同消费者的支持范围见 [消费端研究](NFO_ARTWORK_CONSUMER_RESEARCH.md)。

## 当前问题与代码依据

- `apps/desktop/src/main/nfo/export/nfoExportModule.ts` 将 `snapshot.coverPath` 直接规划为 `coverBasename(profileId, stem)`，除 WebP 转 JPEG 外不改变图片。`makeDocument` 将该文件用作 poster 引用，因此横图也会进入外部软件的竖版海报位。
- `apps/desktop/src/main/nfo/export/nfoExportProfiles.ts` 当前写出 `<thumb aspect="poster">`；普通 profile 用 `<stem>-poster`，Infuse 用 `<stem>`。没有独立横版封面角色。
- `snapshot.posterPath` 在本项目实际用于 fanart/详情背景，名称容易误导，不能当成已存在的竖版海报。
- `apps/desktop/src/renderer/src/styles/library-content.css` 的竖版封面依靠 `object-fit: cover; object-position: right center`，画框比例 7:10；这是显示裁切，不是已保存的图片。
- `apps/desktop/src/renderer/src/coverAspect.ts` 明确将常见 800×538 横版封套的右侧用作竖版展示。项目没有影片封面手动裁剪坐标可直接导出；演员头像裁剪属于另一个用途，不应引入本流程。

## 导出规则

图片方向应按方向信息校正后的像素尺寸判定，不能根据数据库字段名或界面显示模式猜测。

| 输入 | 竖版 poster | 横版封面 | 详情背景 |
|---|---|---|---|
| 横图，宽大于高 | 从右侧裁出 2:3 海报，不拉伸、不放大 | 保留完整横图，单独导出 | 继续按用户的“详情背景”选项处理 |
| 竖图，宽小于高 | 直接使用原图，不二次裁切 | 不生成 | 同上 |
| 正方形 | 保守使用原图作为 poster，并显示比例提示 | 不生成 | 同上 |
| 无法解码或尺寸无效 | 将对应海报标为不可用，给出提示，不把横图伪装成已裁海报 | 能安全读取的原图仍可保留 | 其它文件独立处理 |

新生成海报建议采用 **2:3**。Plex 和 Infuse 的官方海报建议为 1:1.5，Kodi 为 2:3；这是导出产物的比例，不要求修改 Javdex 自身的 7:10 展示布局。

横图右裁属于本产品针对封套的默认策略，**不是 NFO 标准要求**。比如 800×538 横图，可取最右侧约 358×537 区域，生成准确的 2:3 海报。整数裁剪框应在图片内取最大 2:3 矩形并垂直居中，不能只把原图压窄。

普通横向宣传照、主体在左侧的特殊封面可能不适合右裁。首轮在预览中说明“横版封面将从右侧裁剪”，先交付确定性规则；后续有实际需求再加少量手动裁剪能力，不接入演员人脸识别或新增 AI 工作流。

已有竖图若是 7:10 而非 2:3，仍保留原图，满足“原先竖版只输出竖版”的要求；消费端可能存在少量裁边，不宣称所有竖图都原生符合 2:3。

## 文件与图片角色

以 `ABC-123.mp4` 为例，普通 profile：

```text
ABC-123.nfo
ABC-123-poster.jpg       # 竖版原图或从横图生成的竖版海报
ABC-123-landscape.jpg    # 仅横版来源才有，保留完整封面
ABC-123-fanart.jpg       # 独立详情背景；仅在已有并勾选时导出
```

这里的 jpg 仅作示例；未变换的 JPEG/PNG 继续保留原编码，裁剪海报可统一 JPEG，WebP 沿用现有 JPEG 转码路径。不要同时输出 `folder.jpg`、`cover.jpg`、`poster.jpg` 等多个海报别名；多影片共目录时保持 exact-stem 防止串图。

- 普通 profile：poster 沿用现有文件名和 NFO poster 引用，替换内容即可。
- Kodi：可按其 artwork 角色增加 `landscape` 引用；不要把电影横封面误写成剧集用的 `thumb`。
- Jellyfin/Emby：本地 `-landscape` 命名可映射为横版 Thumb；不能把相对 NFO 图片引用当作唯一发现机制。
- Plex 官方 NFO profile：确保 poster 引用竖版文件；完整横图可留在旁边，但没有官方依据保证 Plex 独立消费 `landscape`，因此不写臆造的 XML 字段，也不把横图当成第二张 poster。
- Infuse：竖版仍用既有 `<stem>.<ext>`。不同时额外生成 `<stem>-poster`；横图保存不等于 Infuse 一定显示它。

**横版封套与标准 landscape 不是完全相同的图。** Kodi 的 landscape 推荐 16:9，常见 JAV 封套约 1.49:1。本方案保留封套原比例，用 landscape 作为兼容的独立横图命名，但不将其称为严格 16:9 artwork。若后续要求横图本身也严格适配 16:9，应增加等比留边的呈现策略；不要为凑比例把封套拉伸，或静默裁掉背面内容。这个差异不影响竖版 poster 修复目标。

消费者依据与 URL 汇总在 [消费端研究](NFO_ARTWORK_CONSUMER_RESEARCH.md)。

## 实现范围与计划一致性

建议只增加一个 NFO 导出内部的图片处理模块，例如 `nfoExportArtwork.ts`，负责读取元信息、判断方向、计算裁剪框和编码。继续经 `MediaAssetStore` 公共读取面取得图片，使加密和明文来源遵循同一条路径；不修改数据库封面，也不写回原资产。

现有 `nativeImage` 支持裁剪与 JPEG/PNG 编码，无需为了普通裁剪引入新的大型图片库。但其官方文档明确不处理 EXIF：必须在裁剪前统一方向，并以相同方向计算宽高；不能仅交换尺寸而不旋转像素。现有 `MediaAssetStore.readImageDimensions` 优先使用 nativeImage，只有 fallback 解析 JPEG EXIF，所以也不能直接把它视为已完成像素方向归一化。应在这个窄处理模块解决，并覆盖 EXIF 旋转/镜像的验证。[Electron nativeImage](https://www.electronjs.org/docs/latest/api/native-image)

导出仍使用现有不可变计划：

1. 规划时确定 poster 和横图各自的文件名、源 hash、编码、裁剪区域和转换版本；预览准确展示实际将写入的文件数量。
2. 内容相等判断必须包含图片变换，不能只比较 `storedPath + sourceHash`。同源的原图和裁剪图不是同一个输出内容。
3. 执行时复核来源 hash 和目标状态，按冻结的配方生成文件；不得根据已变化的图片重新决定方向或输出文件集合。
4. 若预览要求精确体积，可在规划阶段编码计数后丢弃临时字节；不要把全库所有图片长期缓存在内存。处理保持逐图、有界内存，并在图片间让出事件循环。
5. 增加 `landscape` 文件类型及中文标签，保留现有 `cover` 对应竖版海报，避免数据库字段重命名等无关改造。
6. 已有“影片封面”选项直接包含上述自动策略，加一行简短说明即可，不必再要求用户分别勾选横图和竖图。

## 已有导出文件与刷新

旧 `<stem>-poster.jpg` 可能已经是横图；如果仍选择“跳过已有文件”，新算法不会替换它，外部软件也就不会改善。应在预览中明确列出旧海报被跳过；用户需对本次导出选择覆盖已有文件，再按目标产品要求刷新图片或元数据。

保留当前显式覆盖和目标 hash/mtime 校验，不静默覆盖或删除目录中的图片。若旧海报为 PNG、新裁剪产物为 JPEG，可能同时留有两个同名不同扩展名的 poster；实现时应尽量保持已有规范目标扩展名，或明确提示存在旧海报候选，不自动删除无法判定归属的文件。

新 NFO 不应产生已知不可用的海报引用。若裁剪规划失败，原图仍作为横图保留；海报缺失须在预览中可见，不应回退为“横图仍作为 poster”并报告成功。

## 验证与交付顺序

- 使用无敏感内容的合成封套测试：左右不同色块，确认只从右侧生成 2:3 图片；原横图完整保留，竖版不重复输出。
- 覆盖竖图、正方形、EXIF 旋转/镜像、坏图、WebP、加密图片和低分辨率；确认不会放大或错误判断方向。
- 验证同目录多影片不会串图、同源不同变换不误判为相同内容、来源变化使计划过期、旧 poster 的跳过/覆盖以及数量和体积统计。
- 扩展现有 profile golden 和导出模块测试，不新增一套重复的格式测试框架。
- 用隔离 Plex NFO 库读回海报尺寸并检查列表展示，使用横版测试源验证最终 poster 为 2:3；Kodi/Jellyfin/Emby 的横图识别按官方合同及至少一项实际消费验证确认。
- 本次仅研究和记录方案；还未执行裁剪、写入媒体文件或验证消费者的新双图效果。
