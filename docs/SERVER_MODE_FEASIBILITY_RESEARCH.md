# 服务端模式可行性研究

> 状态：第一版产品边界已确认；此前功能实验已撤回，服务端功能未实施。本次按用户明确授权完成 monorepo 结构准备，交接执行见 [完整执行计划](SERVER_MODE_EXECUTION_PLAN.md)，未替代既有 ADR。
>
> 研究日期：2026-09-12。代码基线：`cac9f6982eaef6afc34f86f9a51486f8ff10dd2b`。
>
> 输入：用户提供的《服务端模式方案》，从目标、身份与路径到“网页与安全”部分。“已确认”表示用户已确认的产品边界；“本轮确定”表示依据用户授权直接确定的设计细节；“待决定”不得当作已选方案。所有条目均不代表已实施。

## 结论

**技术上可行，建议先做架构验证，再进入完整实施。**“服务端唯一权威资料库 + 桌面运行网络刮削 + 常驻只读网页”与现有领域结构兼容；现有数据库、媒体库隔离、扫描、NFO、图片交割和 HTTP 模块提供了可复用基础。

但这是一项跨运行时、数据身份和远程命令协议的架构改造，不是新增一个 Docker 入口。本次逐项讨论的第一版产品边界已确认，包括客户端与服务端同版本要求；完整管理接口、运行时隔离和故障恢复仍需实现与验证。“互斥模式、单台桌面写入”能降低复杂度，不能消除这些问题。

优先保留原方案的边界：SQLite 与权威图片在服务端；不引入数据库同步；影片通过挂载进入；第一版不在服务器运行 Playwright、不转码、不开放公网。**第一项验证应是纯 Node 进程使用真实 SQLite 和图片存储提供网页，再贯通一条带版本与幂等语义的远程编辑链路。**

## 实施前必须补齐的设计

### 1. 挂载卸载保护（第一版范围已确认）

用户于 2026-09-12 确认：第一版只处理路径卸载造成的不可用与误清理，不处理更换挂载目录、同路径换卷或复制卷的身份识别。补充证据见 [开源项目的挂载与身份处理对照](MOUNT_IDENTITY_REFERENCE_RESEARCH.md)。

- 每个受管根使用固定标记文件（例如 `.javdex-root`），检查可读性，不引入目录 UUID 或显式重绑流程。标记必须位于实际挂载的存储内；独立挂载的子目录应单独注册为根。
- 首次添加根时初始化标记，并在数据库记录已经初始化。只读挂载由管理员预置标记；已初始化的根在标记缺失后不得自动补建，否则会把卸载后的空目录误认作正常存储。
- 扫描开始、扫描结果提交和缺失资源清理前复核标记；不可读时将对应根标为离线，停止该根扫描与文件维护，保留已有归属和资料，不把卸载解释为文件删除。
- 原路径的标记重新可读后自动恢复，不要求人工重绑。仍需通过扫描中卸载、空挂载点及重新挂载实验验证提交与清理保护。
- 服务端不要求跨重启保持相同 inode；继续保留路径包含关系、符号链接逃逸防护、普通文件检查、打开后描述符校验和写入父目录检查。这些文件操作保护不能随挂载判断一起删除。

**范围边界：**另一个目录只要带有同名可读标记，第一版也会视为可用；不承诺检测此类替换。该策略是服务端第一版的明确范围取舍，本地模式继续遵守 [ADR-0024](adr/0024-preserve-media-library-root-identity-continuity.md)。实施时需补充记录服务端适用范围，不能直接放宽本地 guard。以上是已确认设计，尚未实施。

### 2. 管理查询与网页查询必须分权（已确认）

“桌面连接服务器时走同一套网页 DTO”与“同一套管理 UI”存在冲突。网页不可见隐藏成员、归档库、无活动成员的全局影片；演员独立档案、分类图片、清单封面和待确认图片也不能全靠当前可见影片图片端点覆盖。

用户于 2026-09-12 确认：同一个 HTTP 服务、同一个端口提供浏览与管理两组接口，共用底层业务逻辑；网页保持只读浏览范围，桌面获得完整管理能力。第一版沿用单台桌面写入，不引入多用户角色系统。具体路由名称尚属实现细节，例如管理接口可使用 `/api/manage/...`。

已确认的边界如下：

- 浏览器 `/api/...` 沿用现有只读可见范围。
- 桌面管理 API 提供完整的全局目录、媒体库、待确认、编辑预览和管理图片权限；通过 writer 凭据认证，不能接受普通浏览器 Cookie 作为管理授权。
- 桌面界面继续通过 preload/IPC 调用主进程，由主进程按模式选择本地领域服务或远程管理请求；服务端复用领域服务，避免维护两套业务规则。
- 管理 DTO 也不需要暴露服务器绝对磁盘路径。返回根 ID、相对路径、文件名、在线状态、可执行动作与 revision；数据合同应与当前桌面业务字段逐项对照。
- 不将整个 IPC 注册表、任意 SQL、任意路径访问或通用方法调用直接暴露到 HTTP。复用类型不代表现有 IPC 验证可以原样充当远程边界，例如当前 `VIDEO_EDIT` 的 schema 使用通用 object，网络端仍需完整字段验证。

这是对 [ADR-0027](adr/0027-isolate-read-only-lan-web-access.md)“管理只走可信桌面 IPC”的显式扩展：浏览器只读合同保持，新增具备独立凭据的管理 HTTP 表面。以上是已确认设计，尚未实施；接口字段、校验规则和业务覆盖仍需在实施时逐项落实。

### 3. “刮削在桌面”需要细分采集与提交（已确认）

用户于 2026-09-12 确认：桌面负责采集与选择，服务端暂存图片并统一入库；第一版支持安全重试，暂不做断点续传或桌面持久上传队列。职责固定为：桌面运行插件、Playwright、远程请求、图片下载、候选展示和用户选择；服务端执行权威身份校验、字段合并、演员/分类归属判定、待确认记录保存、图片正式引用和数据库提交。桌面可预览结果，但服务端必须针对当前库再次判定。

现有 `deliverCandidate` 用图片变更协调器包裹数据库事务，失败会清理新图片；NFO 也使用相同应用逻辑。把这些变成“客户端先改资料、再逐个上传图片”会破坏现有原子性和回滚语义。

已确认的提交流程如下：

1. 桌面先将图片上传到服务端暂存区；返回不透明 `uploadId`，此时不修改影片资料。
2. 服务端仍校验字节数、格式、像素预算、摘要与当前调用者归属；不能信任客户端声称“已校验”。上传者不能指定落盘路径。
3. 桌面再提交元数据、所选字段、应用模式和暂存 ID；服务端检查图片齐全后完成业务校验与入库。每次提交携带唯一操作编号，重试已完成的提交返回原结果；目标版本等冲突校验遵守下一节已确认的写入规则。
4. 已提交的待确认项及其暂存图片属于服务端权威数据。过期未提交上传由服务端回收；重试已提交请求返回原结果。

数据库和文件系统不能形成一个原生事务；需要沿用并扩展现有暂存、协调提交与恢复机制，失败时保留原资料，并覆盖服务端重启后的恢复。未上传完成的图片允许重传；已提交的待确认资料及图片由服务端持有，不依赖桌面持续在线。以上是已确认设计，尚未实施。服务端无需运行网络刮削器，但仍需内置 NFO 解析、图片处理和元数据应用模块。

### 4. 单写入者仍需要版本、幂等和接管隔离（写入规则已确认）

用户于 2026-09-12 确认第一版采用三项写入保护：资料版本检查、持久操作编号和接管代次。资料发生变化时拒绝旧版本保存，提示刷新后重新确认，不自动合并；同一操作编号重试返回原结果，同编号不同内容拒绝；旧请求在正式提交前再次核验接管代次。有文件维护任务正在执行时，等待完成或安全取消后再允许接管，不提供强制中断后的文件操作回滚。第一版不做离线编辑同步或多桌面协作。以上尚未实施；接管授权与设备丢失恢复见下文已确认规则。

当前 schema 与 IPC 并没有覆盖所有写操作的统一版本合同。例如媒体库有 revision，演员有 revision，而普通影片编辑、评分等接口没有统一的 `expectedRevision`。把它们“沿用”到远程端并非零成本。

单台桌面的多个编辑页、桌面刮削和服务端扫描/NFO 同样会竞争写入。下表列出已确认机制的技术落点，以及服务身份和接口校验的工程建议；具体协议字段仍需细化：

| 概念 | 解决的问题 |
|---|---|
| `serverId` / `catalogId` | 区分同地址上的新服务或替换库，防止旧请求误打到相同数字 ID |
| `writerEpoch` | 每次接管递增；旧客户端请求、旧上传和未提交任务在最终写入前再次核验 |
| 实体/聚合 revision | 防止较早编辑或刮削覆盖扫描、其他页面产生的新状态；需覆盖相关关联表变化 |
| 持久 `operationId` 与请求摘要 | HTTP 响应丢失后可查询或重放原结果；同键不同内容拒绝；幂等结果与数据库变更同事务保存 |
| 应用版本、`apiVersion`、schema 与 capabilities | 第一版应用版本必须相同，仍需通过接口与身份检查；检查失败拒绝远程管理，不降级开放部分管理能力 |

写入 token 轮换只阻止下一次认证，不能自动停止已经通过认证、正在等待 I/O 的旧请求。接管需串行化到提交边界；第一版等待文件维护任务完成或安全取消后才允许接管，等待期间也不能启动会跨越交接的新文件维护任务。不能承诺撤销已经完成的物理写入。

#### 接管授权与设备丢失恢复（已确认）

用户于 2026-09-12 确认：首次绑定从服务器部署端获取一次性管理凭据；正常更换电脑由旧桌面主动生成短期、一次性的交接凭据；旧设备损坏或丢失时，由管理员通过服务器命令生成一次性恢复凭据。第一版不做账号系统，不增加需要长期保管的恢复密码。只知道服务器地址、网页密码、设备名称或网页配对码都不能取得 writer 权限。

生成交接凭据不立即撤销旧桌面权限；新桌面成功领取后才切换控制权，更新接管代次并使旧管理凭据失效。切换遵守已确认的文件维护等待规则。一次性凭据具有有效期，领取成功后作废，服务器重启不能使其重新生效。恢复管理权限保留原资料库，只更换控制权。以上是已确认设计，尚未实施。

bootstrap 应是高熵一次性秘密，不是定义不清的“密文”。领取与作废须持久、原子；容器重启且旧环境变量还在时，已认主实例不能重新开启 bootstrap。正常交接也应处理响应丢失，避免旧令牌已经失效、新令牌却未到达。

HTTP 是原方案接受的可信 LAN 前提，writer 凭据也会经明文链路传输；上述接管协议并不提供传输加密。桌面持久凭据应进入本机凭据存储，并绑定服务身份，不进入普通设置导出。

#### 客户端与服务端版本兼容（已确认）

用户确认第一版仅支持相同应用版本的桌面与服务端连接，同版本仍需通过接口及身份检查。版本不一致时展示两端版本并提示更新，阻止进入远程管理，不自动降级、不回退本地模式；服务端已有任务与网页浏览继续运行。双向迁库也要求两端应用版本一致，预检不符时拒绝，先统一版本。网页使用服务端自带版本，不要求浏览设备安装对应客户端。第一版不维护跨应用版本兼容；更新服务端时需同步更新管理桌面。以上尚未实施。

### 5. 服务端任务必须有断线与重启语义（已确认）

用户于 2026-09-12 确认：桌面断线不取消服务端已接受的任务；服务端自动扫描在桌面离线时照常执行，继续遵守挂载保护与任务互斥。单桌面写入权限限制新的交互修改，不要求服务端任务依赖桌面在线。桌面停止时，其插件采集停止，服务端已接受的提交继续处理。

第一版将任务编号和状态持久保存在服务端，桌面重连后查询状态与结果。服务器重启后，普通扫描可以重新枚举，不要求逐文件续跑；文件维护不自动从头重跑，先根据执行记录核对已完成、未完成或需要检查的部分，再由用户决定后续操作。无法确定结果的操作必须明确标为需要检查，不能默认为未执行。

未确认的维护预览设置有效期，首版暂以 10 分钟为默认值；过期或服务器重启后失效并释放占用资源，需要重新生成。尚未过期的预览在提交前也要复核当前状态。以上是已确认设计，尚未实施。

现有扫描有持久运行记录和启动恢复，但维护 gate、NFO 预览计划与监听器仍在进程内。特别是 NFO 预览持有维护锁与图片稳定读取锁，直接远程化会出现“桌面预览后离线，服务器一直等确认”的问题。

建议定义任务 ID、状态查询、进度序号、取消请求、有限保留的事件/快照，以及预览计划的 TTL。过期、接管或库切换释放未提交计划；重启后明确失效或恢复，不能假装仍能提交旧计划。已接受任务与新写入请求需要不同的离线行为。

原方案“桌面离线则写入失败”按上述已确认边界收敛：桌面离线不能发起新的交互写入，但不阻止服务端自动扫描及已接受的 NFO 等任务继续执行。

### 6. 同一套 UI 仍需能力适配

除远程存储后端外，至少还需处理：

- **图片读取与认证（已确认）**：用户于 2026-09-12 确认沿用桌面 `media://` 图片入口，由主进程按模式选择本地读取或携带管理凭据从服务端获取图片，不将长期管理凭据拼入图片地址。远程桌面使用管理图片接口，覆盖隐藏影片、独立演员、分类、清单和待确认图片；服务端检查当前资料库和对象访问权限。第一版不新增持久离线图片库或图片同步，仅允许临时缓存，不承诺断网完整浏览；图片更新使用版本化地址，切换资料库或模式时隔离缓存并取消旧请求。加载失败显示占位图，恢复连接后允许重试，不阻塞整个页面。以上尚未实施。

#### 迁移范围（已确认）

用户于 2026-09-12 确认第一版支持本地与服务端双向整库迁移，仅迁入空资料库，不合库、不自动覆盖非空目标。影片资料、演员、分类、清单、媒体库归属、权威图片、扫描/NFO 等资料库设置随库迁移；原始影片文件不由迁库功能搬运，桌面插件、播放器、密钥和助手记录留在原桌面。正在执行的任务和未确认的维护预览不跨端续跑，迁移前结束或取消。

路径映射是可选项：每个根目录可以指定目标路径，也可以不指定。指定路径时转换并校验相应资源；不指定时，在迁移后的目标库自动移除该根下的本地文件资源记录，保留影片及媒体库成员关系、隐藏状态、资料和图片，即使影片已没有任何资源也不删除影片。允许所有根都不映射，仅迁移资料及图片。未托管本地文件资源同样需在迁移预览中列明，允许选择移除其记录。该操作只改变目标库的资源记录，不删除磁盘文件，也不从源库移除资源。

迁移预览应列出已映射根、未映射根、将移除的本地文件资源数量和迁移后无资源的影片数量。磁力、网页和直链等非本地资源不因缺少目录映射而删除。用户已经选择不映射后，导入按此选择自动处理，不再要求逐影片确认。以上是已确认设计，尚未实施。

用户进一步确认：存在待确认数据时，不允许发起迁移。此规则覆盖待确认刮削、待确认扫描分组及资源身份等需要用户决策的数据；必须由用户先确认或丢弃，不由迁移过程自动处理，也不随迁移包转移。发起前列出阻塞类别和数量；冻结写入后再次核验，防止预检后产生新的待确认项。该规则替代此前允许携带待确认刮削资料及图片迁移的约定。未确认维护预览也须先结束或取消。实现时还需处理未映射根的无法识别文件快照，不能让旧文件任务在目标端执行。未映射根不作为目标可运行配置，STRM 来源解绑采用第 8 节已确认规则；无资源成员的后续保护采用第 9 节已确认设置转换。不能简单删除所有带 `root_id` 的资源。历史审计保留为历史信息，不作为目标端可执行路径。

#### 迁移执行与数据保护（停写与失败恢复已确认）

用户于 2026-09-12 确认：准备与预检期间源库正常使用；正式迁移前收敛任务、冻结所有写入并再次核验待确认数据，若出现待确认项则退出迁移，由用户先处理。正式迁移期间源库只读、允许浏览，目标仅暂存导入并校验，不开放使用。校验完成后才启用目标写入，源库保留为冻结备份。

确认目标尚未启用时，失败或取消可丢弃目标暂存结果并解除源库冻结；断网导致结果不明时，先核实目标是否启用，核实前源库保持冻结，不自动恢复写入。目标已经启用后不自动解冻源库，回迁应以当前目标库重新执行反向迁移。第一版不要求传输断点续传，可重新迁移，但必须持久保存迁移阶段和结果，重启后仍能确定可写端；取消/失败恢复与目标启用须协调，不能仅凭一次状态查询同时开放两端写入。以上尚未实施；迁移后的设备授权见下文已确认规则。

当前路径身份包括 `video_resources.locator/resource_key/source_identity/strm_source_path`、无法识别快照和审计等数据。图片也不仅是封面，还包括头像源图、裁切图、演员图库、分类图、清单封面与样张。待确认扫描、资源身份和刮削项必须在迁移前处理完毕；未提交上传不作为正式资产迁入。应以 [`schema.ts`](../packages/library/src/db/schema.ts) 及各存储模块制作完整清单，区分活跃路径与历史审计文本，不能全库字符串替换。

按已确认规则展开的执行步骤与工程建议如下：

1. **预检**：首版仅迁入空目标实例；有内容的目标不自动合库。两端应用版本相同、迁移包格式可识别、空间足够，且不存在待确认数据；按上述已确认范围，为各根记录目标路径或不映射的选择，预览不映射时移除本地文件资源记录的影响。已指定的映射无效或存在路径冲突时拒绝迁移，不能自动降级成移除资源。影片文件仍在用户准备的存储位置。
2. **冻结**：停止源端所有写入、自动扫描、刮削交割、NFO与图片回收，收敛进行中的任务。将源库置于迁出状态以防再次启动写入。
3. **生成一致快照**：使用 SQLite Backup API 或正确停库后的快照，并同步冻结图片及网页配置。数据库快照与图片拷贝需要同一个业务冻结窗口；不能在线只复制 `library.db` 而忽略 WAL。SQLite 官方说明见 [WAL](https://www.sqlite.org/wal.html)、[Backup API](https://www.sqlite.org/backup.html)。
4. **目标暂存导入**：带 manifest、版本、数量、摘要和根映射；重建路径派生身份、验证唯一索引、外键、图片引用及待确认数据为空；失败不得替换目标当前库。
5. **提交切换**：校验完成后启用目标，源端保留冻结备份。迁移后的设备授权遵守下文已确认规则；建议发布新 catalog 身份，以隔离旧客户端引用和请求。
6. **回迁**：反向执行同样的可选映射与校验；映射到本地目录时，在目标桌面重新绑定本地物理根身份，不映射则保留影片并移除相应本地文件资源记录。Windows/macOS/Linux 的大小写和分隔符不同，路径冲突必须预检；[`localPathIdentity.ts`](../packages/library/src/localPathIdentity.ts) 当前按运行平台规范化，不能直接拿 Linux `path` 解析旧 Windows 路径。

#### 迁移后的设备授权（已确认）

用户于 2026-09-12 确认迁库保留网页访问偏好等普通设置，监听地址等按目标环境校验，但不继承设备授权。浏览器配对会话、桌面长期管理凭据、一次性交接/恢复凭据和临时播放凭据均不迁移；连接目标服务器时重新绑定管理桌面，网页设备重新配对。迁回本地模式时桌面直接使用本地库，不需要服务器管理凭据，本地网页设备仍需重新配对。正常更换管理电脑而服务器未迁移时，网页设备授权保持不变。以上尚未实施。

#### 迁移工程校验与限制

**图片加密范围（已确认）：**用户在管理合同细化时确认，第一版服务端只保存未加密图片，远程模式隐藏图片加密开关；不新增服务端应用层密钥及其备份恢复方案。本地模式保留原加密功能。源库存在加密资产时须先在源端解密后迁移，不能把“设置已关闭”当作存量已经全部解密。部署端如需静态加密，使用磁盘或文件系统层能力。

加密预检应检查真实存量资产与引用，不仅看设置开关。当前 key 还绑定用户名，除方案提到的 hostname/userData 外也会因运行用户变化失效。已有解密动作可复用，但部分解密失败不得继续迁库。

迁移目标开始接受新写入后，旧备份不再是可无损回退的当前库。恢复旧实例意味着舍弃之后变更或再做一次反向迁移；不承诺自动合并两份库。

### 8. 远程协议与恢复细化（本轮确定，未实施）

用户要求继续细化方案，常规问题直接决定，存在实质产品取舍的问题单独询问。本节细化前述边界，不授权修改运行时代码、数据库或正式 ADR。

#### 服务与资料库身份

`catalogId` 标识整份权威资料库，不是媒体库 `libraryId`。第一版按以下生命周期处理：

| 场景 | 身份与客户端行为 |
|---|---|
| 普通重启、保留数据卷的容器重建 | 保留持久 `serverId`、`catalogId` 和 `writerEpoch`；不因进程重启重新认主 |
| 修改服务器地址或端口 | 地址只是连接位置。先读取握手身份，匹配已绑定身份后才发送管理凭据；地址变化不触发数据迁移 |
| 同地址出现新实例或新资料库 | 身份不匹配时停止进入资料库及重放请求，显示“目标实例或资料库已变化”，由用户重新绑定；不能以名称、地址或版本相同代替身份匹配 |
| 正常更换管理桌面 | 保留服务与资料库身份，原子递增 `writerEpoch` 并替换管理凭据；已受理服务端任务按原规则继续 |
| 双向迁库 | 目标使用自身实例身份，启用时生成新的 `catalogId`；影片等内部 ID 可以保留，但旧实例请求、图片缓存和工作记录不能直接用于目标 |
| 从旧快照恢复为可写实例 | 必须走显式恢复流程，发布新 `catalogId` 并重置设备授权，不能原样恢复旧操作去重记录后自动重放客户端请求 |

第一版不支持复制同一数据目录后同时启动两个可写实例，也不把实例 UUID 当作防克隆措施。同一数据目录启动须有单实例占用检查；快照恢复流程和迁移一样，必须防止两个实例同时被认为是当前可写库。

握手仅返回协议、应用与 schema 版本、实例/资料库身份、就绪状态及必要能力标记，不返回目录内容、磁盘路径或凭据。每个管理请求绑定预期 `serverId`、`catalogId`；写请求再绑定 `writerEpoch`。服务端也须核验这些值，不能只由桌面比较。握手中的 UUID 仅用于防止误连，不为已接受的明文 LAN HTTP 提供密码学身份认证。

#### 管理凭据与交接响应丢失

- 长期管理凭据采用随机不透明秘密，服务端保存摘要，桌面只在主进程访问本机受保护凭据存储；不交给 renderer、不放入 URL、日志或普通设置导出。凭据绑定实例、资料库与当前写入代次。
- 首次绑定、交接和部署端恢复凭据统一采用短期一次性领取流程，默认有效期 10 分钟，由服务器时间判定。新生成的同类凭据替换尚未领取的旧凭据；不得打印到持续滚动的普通服务日志。
- 新桌面先生成并安全保存候选管理秘密和领取编号，再携带一次性凭据提交候选秘密的摘要。服务端在同一事务中核验领取条件、消耗一次性凭据、更新 writer 与代次并保存领取结果；响应不需要传回新秘密。
- 响应丢失时，新桌面先用已保存的候选凭据查询当前绑定状态；相同领取编号和内容的重复请求只能返回原领取结果，不重复接管。一次性凭据即使随后过期，也不会使已经领取的管理凭据失效。已被再次接管的旧领取不得恢复旧权限。
- 文件维护阻塞交接时，不能提前消费一次性凭据或撤销旧 writer；进入交接等待后阻止新文件维护启动，完成等待后再次核验凭据有效期。过期或取消即退出等待，允许重新发起。
- 本机安全凭据存储不可用时，阻止持久绑定并提示修复系统钥匙串，不静默退回普通文件保存。Electron 官方说明 Linux 的 `basic_text` 后端不提供应有的秘密保护，实施时须检测该情况。[Electron safeStorage](https://github.com/electron/electron/blob/main/docs/api/safe-storage.md)

#### 请求版本、幂等与任务受理

第一版采用明确的用例请求，不设计通用远程 IPC 分发器。写请求包含操作编号、预期身份、代次、所需聚合版本及用例数据。服务端按已验证字段生成稳定摘要；JSON 字段顺序或传输重试不能改变同一请求的语义，上传 ID、选择字段、应用模式与预期版本必须纳入摘要。

短数据库修改在提交事务中依次复核身份/写入代次、查找操作结果、核验版本与业务条件，再同时写入业务数据和操作回执。查找已有回执先于版本冲突判断，防止成功重试被自己的上一次修改误判为版本冲突；认证仍先于回执读取，旧 writer 不能借查询历史结果恢复管理访问。

| 情况 | 固定行为 |
|---|---|
| 同编号、同内容、已成功 | 返回原回执及当时的结果版本，不再次执行；读取最新状态是另一次查询 |
| 同编号、不同内容 | 拒绝编号复用，不覆盖原记录 |
| 同编号、任务已受理 | 返回原任务 ID，不再排队；任务受理记录与操作回执在同一事务提交 |
| 版本冲突或最终业务拒绝 | 返回稳定错误；修改内容或刷新后重试必须使用新操作编号 |
| 超时、断线、服务暂不可用 | 显示“结果待核实”，以原编号查询或重试，不自动更换编号 |
| 重启后文件操作结果不确定 | 转入“需要检查”，阻止重复执行；不能用通用重试绕过文件恢复核对 |

第一版不自动删除操作编号、摘要及终态的小型去重回执，在当前 `catalogId` 生命周期内防止旧编号再次执行；回执仅保存稳定结果 ID、版本、计数和错误码，不保存整份请求、图片字节或凭据。任务日志、进度事件可单独限量清理，不能因此丢失受理和终态依据。未来增加回执期限必须同时设计过期编号的拒绝协议，不能只删记录。

版本覆盖业务聚合而非每个 UI 控件：影片资料及其关联变更递增影片版本，媒体库成员/资源变化提供相应集合版本；批量操作带上实际依赖的目标版本。评分、扫描/NFO、刮削和其它入口的同类变更遵循同一规则。精确版本归属需形成用例清单，不能用只覆盖部分字段的现有 revision 宣称已完成。

“已受理”以数据库持久事务为界：短修改以业务提交为界，长期任务以持久任务入队为界。只通过 HTTP 认证或只上传图片都不等于任务已受理。接管使旧的未受理写请求、未提交预览和上传失效；已经正式受理的任务由服务端拥有，继续按其记录执行，不能在每一步机械套用旧桌面的 epoch 而使其半途失效。

#### 播放验证对象与凭据

先选 **mpv** 作为第一款验证播放器，原因是官方提供明确的命令行 URL 输入和网络控制选项；这是验证对象选择，不是已经验证兼容。验证时记录具体二进制版本和平台，不把文档支持推断为实测通过。[mpv 官方手册](https://mpv.io/manual/stable/)

- 桌面设置播放器程序路径，主进程用参数数组启动，不能拼接 shell 命令。第一版不提供任意命令模板或自动安装播放器。
- 服务端本地影片资源使用资源 ID 对应的原始流端点；每次播放创建独立随机播放凭据，限制到资料库、媒体库、资源及资源定位版本，只允许 HEAD/GET/Range。凭据出现在播放 URL 时，日志须遮蔽，且不能重定向到第三方携带该凭据。
- 为避免依赖桌面在线续期，第一版采用从签发起 **12 小时固定有效期**，不滑动延长、不因 HEAD 或一次 Range 消耗。到期后须从 Javdex 再次点击播放；服务端到期终止仍在发送的旧流，已经进入播放器缓存的字节无法撤回。
- 凭据不绑定播放器 IP 或单条 TCP 连接，允许同一次播放建立多次 Range 请求。服务端重启后允许仍有效的已持久凭据继续使用，但不承诺播放器自动续播。
- 每次打开流仍校验资源归属、当前定位版本与文件 guard。资源删除、定位变化、管理权接管、资料库迁移/恢复均使相关旧播放凭据失效；普通资料标题修改不终止播放。接管完成后停止旧代次尚在发送的管理播放流，网页独立会话仍按既有确认规则处理。
- 原有网页、磁力和 ED2K 资源继续在桌面通过对应系统处理器打开；网络视频直链交给指定播放器直接访问，不经过服务端任意 URL 代理，不附加 Javdex 管理或播放凭据。第一版不新增第三方请求头配置、地址续签或转码。

12 小时是本轮确定的首版默认值，可在真实长片、暂停后续播实验发现问题时再调整；不增加独立的续期服务或播放心跳协议。

#### STRM 迁移的来源解绑（已确认）

已确认“不映射根也保留非本地资源”，但 STRM 不能简单清空路径字段：[ADR-0019](adr/0019-identify-strm-resources-by-source-file.md) 允许不同源文件指向同一链接并保持独立资源，普通手动链接则按目标去重；当前 [`schema.ts`](../packages/library/src/db/schema.ts) 的资源唯一键作用于整个媒体库，而非单部影片。解绑会触及现有身份规则，属于需要用户决定的产品取舍。

例：同一媒体库的 `a.strm` 与 `b.strm` 指向相同 URL，分别归属影片甲、乙；同库还可能有该 URL 的手动链接。把它们全部转成普通链接将产生唯一键冲突，不能自动选择一部影片接收、自动合并影片或丢弃某条资源。

用户已选择首版转成普通链接，按现有规范化目标生成身份；任何冲突都在迁移预检中列出涉及的影片和资源并阻止发起，由用户先在源库处理，再重新预检。即使同影片内部发生重复，也不静默合并。无冲突时保留资源 ID、影片归属、展示信息、主资源和添加时间，清除活动的源路径、源身份和根关联，今后不再受原 STRM 文件扫描同步；源文件与源库均不改动。目标可访问性不作为成功承诺，链接是否有效不能靠迁移时主动访问远端来判断。

第一版不新增“已脱离源文件的 STRM 资源”身份。这里对 ADR-0019 增加的是显式迁移时的解绑边界：文件托管期间仍按源文件标识，解绑后遵守普通链接去重规则。已映射源目录的 STRM 仍保留文件托管身份，不参与此解绑；目标上须重新读取校验，内容与冻结快照不符时拒绝该映射，不在迁移中自动更新链接。

### 9. 迁移状态与未映射目录细化（本轮确定，未实施）

#### 未映射根的表示

不把源机器绝对路径复制成目标可运行根配置，也不制造虚拟目录占位。未映射根的名称、来源路径和迁移选择只进入迁移报告及历史审计；目标不创建该根的扫描配置，不自动创建目录或标记文件。媒体库本身、库级规则与成员保留，零根媒体库允许存在，其自动扫描没有目录可处理。

映射根只保留业务配置，路径、标记初始化状态和文件 guard 身份必须在目标环境重新建立。目标是本地模式时仍遵守 ADR-0024，不能把服务端的简化标记策略带回本地模式。所有源端活跃扫描快照与未识别文件工作项都不能原样进入目标调度；已映射根在目标重新枚举，未映射根不生成可执行快照，历史审计仍只读保存。属于待确认决策的数据继续遵守迁移前阻塞规则，不得借“重建快照”丢弃待确认项。

迁移预览在已有资源移除数量之外，增加 STRM 转换数量、冲突清单、将省略的根配置、需要重新扫描的范围；普通主资源被移除时按 ADR-0014 为剩余资源确定主资源，无资源则清除主资源引用。预览后任何相关写入都会使原计划失效，正式冻结后重新计算并比对影响，发生变化须返回预览，不能直接执行变化后的结果。

#### 无资源成员后续保护（已确认）

现有扫描允许按媒体库设置自动移除无资源成员，但固定成员受到保护，见 [ADR-0028](adr/0028-batch-scan-cleanup-at-commit-boundaries.md)。迁移当下保留成员还不足以保证下一次扫描保留。

用户选择在目标端关闭受影响媒体库的“自动移除无资源成员”设置，不自动将成员设为固定。受影响指至少一个成员因本次不映射/移除本地资源而从有资源变为无资源；只有目录配置被省略、但成员仍有其它资源时不触发该设置转换。原本已关闭的设置继续关闭，无此类变化的媒体库保持原设置。固定状态、隐藏状态及成员关系均按源库保留。

迁移预览逐库列出这项设置变更，并说明它也会保留该库今后因其它原因产生的无资源成员；用户可以以后自行重新开启。源库设置不改动。此项是对“资料库设置随迁移保留”的已确认例外，双向迁移均适用。验收必须覆盖自动扫描以及手动扫描，证明首次扫描不会把刚保留的无资源成员移出媒体库。

#### 启用与取消的持久状态

迁移用独立的 `migrationId`、源/目标身份、冻结快照摘要和映射摘要绑定一次操作。它与普通管理请求分开授权：目标部署端提供只允许向指定空目标暂存、查询和完成本次迁移的一次性迁移授权，不复用网页凭据，也不迁入源端管理凭据。领取后转换为本次迁移范围内的恢复凭据，以便超时后查询；秘密不进入迁移包。

目标未启用时只允许迁移控制请求，不因源端桌面发来普通管理请求而提前开放使用。正式接管管理桌面仍遵守迁移后重新绑定的已确认规则。状态名为方案术语，不预先规定数据库表或实现文件。

| 阶段 | 源端状态 | 目标状态与允许动作 |
|---|---|---|
| 准备 | 正常使用 | 检查空目标、身份、版本、映射、空间和阻塞数据；准备阶段不是迁移已开始 |
| 冻结与传输 | 持久冻结，停止写入与后台任务 | 本次迁移独占目标，暂存传输数据；重启后仍不可作为普通资料库使用 |
| 校验完成 | 保持冻结 | 将快照及映射摘要、校验结果持久保存为“就绪”，等待源端明确的启用许可 |
| 发出启用许可 | 先持久记录已授权启用，再发送许可；此后不得单方面解冻 | 许可须绑定本次就绪快照；目标原子选择“启用”或“已放弃”，不能两者都成立 |
| 目标启用 | 冻结备份 | 原子发布新 catalog 身份与已启用标记，再开放目标任务和写入；相同许可重试返回同一结果 |
| 取消或失败 | 只有取得目标持久“已放弃”的确定结果后才解除冻结 | 原子标记该迁移已放弃，拒绝以后所有迟到的启用许可；临时文件可稍后清理 |

取消与启用在目标同一持久决策点串行化。如果启用先完成，取消返回“已启用”并保持源冻结；如果放弃先完成，迟到的启用永远被拒绝。仅查询到“尚未启用”不是安全解冻依据，必须完成不可再启用的放弃决策。

网络超时不改变任何一端的可写性。目标不可达或恢复凭据丢失时，界面显示待核实，源端继续冻结；不提供基于超时的强制解冻按钮。目标状态存储损坏或整个实例丢失属于人工灾难恢复，须先确保原目标不能继续提供写入，不能当作普通迁移取消处理。

启用前预留的恢复身份必须能在目标更换 catalog 身份后查询本次迁移结果，但不能借此读取或修改普通影片资料。终态记录不得随暂存文件清理而删除。目标暂存目录转为正式库的操作也需要恢复记录，启动时未完成验证/发布的目录不得被当成已就绪库。

源端停止或桌面退出后，迁移恢复只查询或推进上述持久状态；不要求自动重传所有内容。第一版失败后重新传输仍可复用明确未启用的受控流程，但新快照必须使用新的迁移编号，不能把旧启用许可用于新数据。

## Docker 与纯 Node 运行要求

1. **独立入口与依赖边界**：服务端装配数据库、图片存储、查询 worker、文件 guard、扫描/NFO和 HTTP；不复用整个 `appMain`。注入路径、设置、凭据及事件端口，生产服务端依赖图不得加载 Electron、插件运行时或 Playwright。
2. **独立安装平台依赖**：仓库 `postinstall` 调用 Electron rebuild，但服务端不应照搬整个桌面安装流程或 `node_modules`。本次核查 `better-sqlite3@13.0.3` 的安装包与加载器，确认它提供按平台选择的预构建模块；Linux Node 实测无需源码重编译。应区分 Node-API 预构建模块与依赖特定运行时 ABI 的扩展，不能笼统认定所有 Electron 原生模块都必须重编译。`sharp` 仍需安装 Linux/架构/libc 对应包；本次使用 glibc 镜像验证。一般运行时区别见 [Electron 原生模块说明](https://github.com/electron/electron/blob/main/docs/tutorial/using-native-node-modules.md)。
3. **数据卷**：`/data` 的 SQLite 应落在宿主本地文件系统，而非 NFS/SMB 网络共享；影片挂载可独立指向 NAS 数据。Docker named volume 也可以使用网络驱动，所以“是 volume”本身不能证明数据库存储合格。[Docker volumes](https://docs.docker.com/engine/storage/volumes/)
4. **挂载和权限**：声明 UID/GID、目录可写性及空间检查；浏览/扫描可用只读影片挂载，NFO写入、重命名、物理删除要求相应写权限。避免挂载路径拼错后创建空目录；Compose 长语法可设置 `bind.create_host_path: false`。不过宿主 NAS 卷掉线后挂载点目录仍存在的情况，还必须通过挂载内标记检测阻止误清理。[Compose services](https://docs.docker.com/reference/compose-file/services/)、[Bind mounts](https://docs.docker.com/engine/storage/bind-mounts/)
5. **地址配置**：单独配置公开访问 authority，例如 `192.168.1.10:18096`，与容器监听 `0.0.0.0:8096` 分离。当前代码按本机网卡及 socket 本地端口验证 Host，在端口映射下可能拒绝合法请求；不得改成接受任意私网 Host，也不默认信任转发头。
6. **LAN 边界**：compose 显式绑定宿主 LAN IPv4，配合宿主防火墙。Docker 端口发布默认可覆盖所有接口；不同网络路径/NAT下应用观察到的 peer 地址需要实测，不能只靠容器里的私网来源检查证明服务未公开。[Docker port publishing](https://docs.docker.com/engine/network/port-publishing/)
7. **生命周期**：启动先迁移/恢复再就绪；停止时停止接收写入、收敛任务、关闭查询 worker、HTTP 和数据库。提供区分存活/就绪的检查，避免迁移失败仍显示可用。升级失败保留可恢复快照；不要让旧镜像直接打开较新 schema。

这些是现有代码与官方运行约束推导出的工程要求；本次没有完成 Linux 镜像构建或 NAS 验收。

对后续设计有参考价值的结论：

- HTTP 与目录查询应通过明确接口获得图片能力，避免模块导入隐式加载 Electron；独立入口和构建仍需单独设计。
- 文件变更与数据库事务需要共享提交和补偿规则；进程内排队只能处理并发，不能代替崩溃恢复。
- 上传记录应先于文件写入落盘；资源引用与上传记录的消费状态应在同一 SQLite 事务中提交，恢复清理须可重复执行。
- 对外开放写入接口前，仍需设计并验证写入凭据、writerEpoch 最终提交校验、版本冲突和操作幂等协议。
