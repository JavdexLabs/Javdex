# 服务端便捷更新机制研究

研究日期：2026-10-13。状态：研究记录，开发代码已进入实施。研究依据为 `dev` 的 `3e0b581a1acbda92f09a5fd261eb15fba8c5f70e` 及当时未提交的版本整理改动；正式发布基线为 0.8.0。本文不代表已发布新版本或完成容器更新验收。

## 1. 结论

后续：用户接受更新中断，随后确认只部署一个容器；宿主机助手的未发布实现由容器内常驻管理父进程、非 root 业务子进程及完整发行包替代。本文保留最初研究时的取舍依据，不作为当前安装步骤；现行部署与验证边界见 [服务端更新](SERVER_UPDATE.md)，决定见 [ADR-0031](adr/0031-manage-server-releases-inside-one-container.md)。

建议采用 **客户端提供更新入口，独立更新助手执行，短暂停服后替换完整版本**。在线下载与客户端上传离线包可以共用后续安装流程。第一种执行后端优先覆盖现有官方 Docker 部署（Linux amd64 / arm64）。

不建议首版做不停机代码热替换，也不建议让业务服务直接覆盖自己的文件或管理 Docker。下载可以在服务运行时完成；备份、数据库迁移和切换需要维护窗口。窗口长度取决于数据量、备份介质和迁移，不能预先承诺“几秒完成”。

现有 0.8.0 没有更新助手或更新 API，需要用户在宿主机完成一次安装/部署调整。新客户端无法凭空给旧服务增加远程更新能力。

## 3. 成熟产品和基础设施的做法

以下为来源事实，后续选型为 Javdex 的设计推论。

- **Jellyfin**：官方容器升级示例采用停旧容器、拉镜像、启动新容器；降回旧版的流程包含恢复数据和配置备份。[升级与降级](https://jellyfin.org/docs/general/testing/upgrades/)
- **Nextcloud**：内置 updater 会检查写权限、进入维护模式、下载并替换代码，再执行迁移。它备份的是代码，不包含数据库和用户数据。[内置 updater](https://docs.nextcloud.com/server/stable/admin_manual/maintenance/update.html)
- **Nextcloud 容器**：Nextcloud 组织下的社区维护镜像采用拉取新镜像并重建容器，启动脚本处理升级，保留全部所需数据卷。[官方组织仓库](https://github.com/nextcloud/docker#update-to-a-newer-version)
- **Plex 是需要区分的例外**：官方 Docker 的 `public` / `beta` 标签会在启动或重启时下载并安装 PMS；固定版本标签是另一种方式。这证明启动器自更新可行，但不是进程不停机热替换，也不是通用的网页上传包机制。[Plex Docker Tags](https://github.com/plexinc/pms-docker#tags)
- **Docker Compose**：镜像或配置变化时，`up` 会停止并重建容器，保留挂载卷；`--wait` 只等待 running/healthy，仍取决于配置了什么健康检查。[Compose up](https://docs.docker.com/reference/cli/docker/compose/up/)
- **Docker 离线分发**：`docker image load` 可读取镜像归档并恢复镜像和标签。Javdex 若支持上传，应明确产物为经测试的 Docker image archive；不能假设任意 ZIP 或 OCI layout 都能直接 load。[image load](https://docs.docker.com/reference/cli/docker/image/load/)

## 4. 候选方案比较

| 方案 | 用户体验 | 适用性 / 代价 | 建议 |
| --- | --- | --- | --- |
| 运行中替换 JS 模块 | 理想上不重启 | 需处理模块状态、worker、连接、原生依赖与数据库迁移，故障定位复杂 | 首版不采用 |
| 两个实例滚动/蓝绿切换 | 可缩短连接中断 | 当前要求单宿主写库，迁移与旧代码可能不兼容；需额外代理、状态和数据库演进设计 | 首版不采用 |
| 容器内部启动器下载新程序 | 一次重启安装 | 可以实现，但程序、基础镜像和原生依赖版本分离，增加发布组合；仍会停服 | 非首选 |
| 宿主机一键更新命令 | 登录 NAS/SSH 后执行一次命令 | 范围小，可先建立备份、替换和恢复闭环 | 最低成本可交付阶段 |
| 客户端按钮 + 独立更新助手 | 点击后查看进度并自动重连 | 需一次安装助手及受限的更新授权；能独立于业务进程恢复 | 目标方案 |
| 客户端上传离线包 + 同一助手 | NAS 不需访问镜像仓库 | 需离线产物、签名、上传暂存和空间管理 | 在线流程稳定后接入 |
| 非 Docker 独立安装包 | 可做类似桌面安装器 | 需自带/约束 Node、原生库、OS/架构/libc，适配进程管理器 | 后续单独做执行后端 |

Node-API 的 ABI 稳定性不自动涵盖所有 Node API 和外部库，因此不能把“都是 Node 程序”作为任意平台通用更新包的依据。[Node 官方说明](https://nodejs.org/download/release/v22.23.0/docs/api/n-api.html#implications-of-abi-stability)

## 5. 推荐用户流程

客户端“服务端更新”显示当前版本、可用目标版本、是否需要同步更新桌面、预计需要的存储空间，以及当前是否有播放/扫描/维护任务。

1. 选择在线更新，或者选择已下载的官方离线包。
2. 先下载/上传、校验和准备目标镜像，期间继续使用当前服务。
3. 确认维护窗口；有阻塞任务时显示原因，等待完成或由用户取消。允许预约“空闲后更新”，首版不静默终止任务。
4. 更新助手停服、完成一致性备份、切换镜像并启动验证。
5. 验证通过后开放业务访问；客户端重连并核对服务器身份、版本。失败时展示恢复结果和可导出的诊断日志。

进度按“准备、备份、安装、验证、完成/恢复”显示；不把下载百分比当总体百分比。播放恢复属于额外客户端能力，未实现前提示会中断播放，不承诺无感。

服务端能访问 GHCR 时，在线方式直接获取镜像。服务端无法访问、桌面能联网时，桌面下载目标服务器架构的离线包后上传；桌面完全离线时用户手动选择同一种包。包的架构由服务器决定，与桌面是 Windows/macOS/Linux 无关。

## 6. 更新助手的边界

建议助手运行在业务容器之外，持久状态也放在不会随业务容器替换、不会被资料库回滚覆盖的位置。Linux Docker 首版优先宿主机服务/命令；sidecar 可以另作安装形态，但读取 Docker socket 仍意味着高权限，并不会因为放进容器就天然受限。

职责限定为：识别已登记的 Javdex 部署、准备指定官方版本、校验包、停启目标服务、保存快照、验证和恢复。客户端只提交目标 release / 已校验包标识，不允许提交 shell、任意 Compose、挂载路径或任意镜像名。既有 Compose 配置由宿主机管理员登记，助手保留项目身份、媒体挂载、端口、环境和卷名，不能通过重建丢失原有配置。

默认 rootful Docker 的管理权限可以影响宿主机，属于比影片编辑更强的权限。Docker 官方明确要求仅让可信用户控制 daemon。[Docker 安全边界](https://docs.docker.com/engine/security/#docker-daemon-attack-surface)

建议部署者在首次安装时显式开启远程更新，并绑定独立可撤销的更新凭据；资料库 writer 权限不能自动等同于部署管理员权限。远程控制使用经身份校验的加密通道（例如配对后固定证书的 TLS），助手本地执行部分可用 Unix socket。若未来让业务 HTTP 代理请求，助手仍须独立校验授权，业务进程停止期间也要有可查询进度/恢复的入口。

独立、窄范围的 `updateProtocolVersion` 用于发现能力、检查、传输、执行和查询任务；保持有界向后兼容。普通资料编辑继续要求相同应用版本。助手和新客户端的兼容下限必须写入更新元数据；助手自身更新应使用单独恢复流程，首版可保留宿主机升级方式。

## 7. 安装与失败恢复必须共同设计

建议持久状态机：

`准备 → 已验证 → 排空任务 → 已停服 → 已备份 → 启动待验证版本 → 验证通过 → 开放业务`

失败分为 `原版本继续服务`、`恢复中`、`已恢复`、`需要人工恢复`，不能把“进程启动了”直接记作成功。重复点击或网络重试复用同一任务 ID；桌面断网不取消已经开始的安装。助手/机器重启后根据持久记录恢复，并禁止两个更新任务同时操作同一部署。

关键实现条件：

- **先预检再停机**：检查版本/迁移路径、目标架构、签名、下载完整性、镜像及备份所需空间，保留旧镜像；只在准备完成后进入维护。
- **真正停止全部写入**：更新维护状态要覆盖 HTTP 写入、自动扫描、刮削提交、备份恢复、文件重命名/NFO 导出等任务。已有单任务 gate 与资料库 frozen 可参考，但不足以直接声明已有全局更新屏障。
- **确认旧进程退出**：助手确认旧容器停止后才能启动新容器，不能依赖容器内部 PID 文件进行跨容器排他；停机超时应记录失败并检查状态，不盲目继续备份/启动。
- **一致性快照**：在旧进程完全停止后，快照 `dataDir`、独立 `imagesDir` 和配置/凭据；SQLite WAL 存在时保留完整文件集合。快照放在独立目录/卷，避免递归复制自身；检查可恢复性、权限和空间，定义保留策略。原视频不必每次复制，但验证阶段不能执行修改媒体文件的后台任务。
- **待验证启动模式是新增能力**：在恢复任务、后台调度和业务访问之前识别更新状态；迁移和必要恢复只能在可回滚范围内运行。现有 runtime 自动恢复文件维护，因此不能只在 HTTP 外层加个“维护中”就宣称安全。
- **验证真实服务**：除 `/ready` 外，验证目标应用/构建版本、schema、原 serverId/catalogId、worker 查询、关键读操作；`/ready` 本身目前不提供这些证明。运行中的容器不等于迁移、数据身份和查询都正确。
- **验证后才开放写入**：在此之前失败可停止新服务、恢复完整快照及旧镜像再验旧服务。恢复也失败时保持停止并保留现场。开放业务后再发现问题，不能自动恢复旧快照，否则会丢掉用户新写入，必须由管理员选择恢复时点。
- **事务不是完整回退**：迁移 SQL 的事务只覆盖相应数据库操作；迁移已经提交后，新进程或图片/配置处理仍可能失败。跨 schema 回退必须关联旧程序和迁移前数据，不能仅切换镜像或降低 `user_version`。

Docker restart policy 不负责选择新镜像、安装升级或恢复数据库；手动停止也有特定重启行为，更新助手必须显式协调停启。[Docker restart policy](https://docs.docker.com/engine/containers/start-containers-automatically/)

## 8. 在线与离线包的共同发布合同

建议新增签名发布清单，绑定 release 版本、源码构建标识、通道、OS/架构、镜像 digest、归档哈希/大小、允许的源版本及 schema、目标 schema、最小助手/更新协议版本。

在线与离线都绑定同一发布身份，但镜像 manifest digest、镜像配置 ID、归档 SHA-256 是不同对象；需要在发布流水线建立映射并分别验证，不能直接互相比相等。离线包使用对应架构的 Docker image archive，附同一发布的签名元数据；载入后仍核对实际目标镜像身份，并避免载入未授权的附带镜像/标签。

SHA-256 用于检测内容变化；把包和校验文本一起替换，仍能通过普通哈希比对。自动执行的包应使用预置信任根校验签名，同时检查过期、版本回退和密钥轮换。TUF 提供此类更新元数据与信任管理设计，可在实现时评估成熟实现；仅采用一个签名文件不能声称完整实现 TUF。[TUF 概述](https://theupdateframework.io/docs/overview/)

上传需要体积/解压配额、断点续传、隔离暂存、过期清理和幂等任务。校验前不导入 Docker、不执行包内脚本；归档需防止路径穿越、符号链接逃逸和解压膨胀。完全离线的验证所需公钥和证明应预先具备，不临时要求访问外网才能完成安装。

非 Docker 若以后接入，使用版本目录和独立启动器切换，提供匹配平台的完整运行产物；不要让用户升级时在线编译原生依赖。它与 Docker 可以共享清单和流程语义，但不能共享同一个安装包或假设所有 OS 的进程/文件替换相同。

## 9. 建议实施顺序与验收边界

这是工作拆分建议，不是已创建的 Issue 或已批准的实施计划。

1. **更新执行基础**：先交付宿主机命令，固定版本准备、停机快照、替换、验证、恢复和持久任务记录；补发布元数据。范围优先官方 Linux Docker 两架构。
2. **客户端一键更新**：部署独立助手、建立更新配对与兼容协议，接入在线下载、维护状态和重连；实现待验证启动模式及验证通过后的业务开放。
3. **离线更新包**：CI 生成双架构的独立归档，客户端选择/下载/续传，复用相同执行流程。
4. **按实际需求扩展**：非 Docker 独立包、定时空闲更新、更多 NAS 安装形态。进程不停机热替换不列为默认目标。

未来实现验收需包含：正式旧库升级且身份/评分/清单保留；版本不一致仍能使用更新通道；错误架构/签名/磁盘不足在停机前失败；忙碌任务正确阻挡；上传断线与助手重启可续；迁移或新服务验证失败后完整恢复；恢复失败不开放错误数据；已开放业务后不自动抹掉新写入；两个架构真实容器升级及离线安装。

本轮仅做代码与官方资料核查，新增本文；没有部署助手、更新真实服务、上传程序包或执行更新故障实验。
