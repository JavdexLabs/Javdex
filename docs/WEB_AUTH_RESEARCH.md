# Javdex 局域网 Web 便捷认证研究

研究日期：2026-09-08。本文保留实施前的研究结论与建议。

后续进展：用户已选择实施第一阶段；桌面配对、有限期记住设备与撤销已落地，当前使用方式与边界见 [LAN_WEB.md](LAN_WEB.md)。下文“未实施”“待批准”等表述均指研究当时的状态。

核验状态：父代理已完成 Jellyfin、Plex、W3C、RFC 与 OWASP 官方来源核验；本轮研究已收敛，不再扩展来源。该核验不等于产品实现、兼容性测试或功能实施授权。

本文只研究认证与登录保持，不修改产品代码，不授权新增功能。场景为：Electron 桌面端是可信管理端；手机、平板、电脑、电视的 Web 客户端只读浏览与播放视频。外部证据仅采用产品官方文档、官方源码及标准组织规范；“来源事实”“当前实现”“项目建议”分别标明。已并入本轮补充核验重点：RFC 的 TLS 前提、Jellyfin 官方码长措辞、稳定访问地址、桌面独占批准权及 HTTP 持久令牌风险；不代表已经进行浏览器实测或实现验证。

## 1. 结论与选型

**项目建议：第一步采用 Jellyfin 式“新设备显示 6 位配对码 → 桌面批准 → 新设备登录”，配合可撤销的可信设备记录和有限期持久登录。** 这能减少电视遥控器输入及各设备反复输入密码，又与现有桌面管理边界一致。

配对码只标识短期授权请求；领取登录凭证另需高熵秘密。二维码只是地址或临时配对信息的载体。二者都不能成为永不过期的 bearer token，也不能直接访问媒体。

| 候选方式 | 对本项目的价值 | 当前判断（项目建议） |
| --- | --- | --- |
| Jellyfin 式桌面批准配对 | 无需新设备输入密码；无需云账号 | 第一阶段主入口，审批仅在可信桌面 |
| Plex 式 TV linking | 大屏短码、小屏确认的交互清楚 | 借鉴交互，不引入 Plex 云账号体系 |
| RFC 8628 设备授权 | 提供双码、轮询、过期及二维码的规范参考 | 借鉴安全模型；当前 HTTP 方案不能声称符合该 RFC |
| 可信设备持久登录 | 解决服务重启后重复登录 | 与配对一起设计，必须有期限、撤销和服务端持久状态 |
| Passkey / WebAuthn | 适合支持相应能力的手机、电脑快速再次认证 | 稳定域名及可信 HTTPS 到位后再评估；保留电视配对入口 |

## 2. 当前实现与容易混淆的寿命

**当前实现（本地工作树基线 `ba98743`）：** 核对了 [`auth.ts`](../apps/desktop/src/main/web/auth.ts) 与 [`server.ts`](../apps/desktop/src/main/web/server.ts)。

- 密码使用随机盐与 scrypt；要求 12–128 字符。会话 token 为 32 字节随机值，服务端只在内存 Map 保留其 SHA-256 摘要和时间。
- 会话闲置上限 24 小时、绝对上限 7 天；每次成功 `check()` 更新 `touched`，不更新 `created`。重启会丢失会话，停止服务与显式撤销也会清空。
- Cookie 已有 `HttpOnly; SameSite=Strict; Path=/; Max-Age=604800`，没有 `Secure`。因此客户端 Cookie 已可持久保存，但服务端认证状态并未持久化；“已有七天 Cookie”不等于“重启后仍登录”。
- 有效截止是闲置截止、绝对截止、撤销及服务状态共同约束的结果。活跃使用不能突破七天；Cookie 保留七天也不能突破闲置一天。现有请求检查更新闲置时间，不代表一次正在传输的视频流持续刷新会话。
- 服务使用 `node:http`，默认监听 `0.0.0.0`。对端必须是允许的本地/私网地址，Host 必须匹配本机允许的 IPv4 地址或 `localhost` 加实际端口；Origin 固定按 `http://` 校验，忽略 forwarded headers。`isLocalPeer()` 也有部分 IPv6 判断，但对外地址和 Host 白名单并不构成通用 IPv6、域名或反代支持。
- 当前 POST 只有登录、登出例外；其他写请求拒绝。目录、详情、图片和视频 API 都需要会话。

**项目推论：** 便捷认证有两个独立问题：首次如何授权、后续如何保持登录。只加短码不会解决重启清空；只延长 Cookie 也不会解决服务端状态丢失。持久化必须保留原始授权时间，不能每次启动将七天重新计时。

## 3. 官方产品与标准事实

### 3.1 Jellyfin Quick Connect：码显示在待登录设备上

**来源事实：** 新设备 A 选择 Quick Connect，显示一个 6 字符码（当前官方原文为 **6-character**）；已登录设备 B 打开 `Settings > Quick Connect`，输入 A 的码并确认，A 自动登录。无效或过期需要重试。不是在未登录电视上输入管理员的固定 PIN，也不是把服务器密码编码成二维码。[Jellyfin 官方使用说明](https://jellyfin.org/docs/general/server/quick-connect/)

为核实“6 位数字”及协议细节，以下固定查看官方 **v10.10.7** 源码样本，不声称它代表研究日最新版本：

- `CodeLength = 6`，实际生成范围为 `100000`–`999999`；另生成 32 字节随机 `Secret`。未批准请求按 10 分钟窗口清理。该十分钟是版本实现值，不是所有产品应遵循的标准。
- `POST /QuickConnect/Initiate` 返回 Code 与 Secret；新设备通过 `GET /QuickConnect/Connect?secret=...` 查询；已登录端调用受 `[Authorize]` 保护的 `POST /QuickConnect/Authorize`，提交 Code。
- 授权后，新设备以 Secret 调用 `POST /Users/AuthenticateWithQuickConnect` 取得认证结果。显示码和领取认证结果的秘密分工不同。

来源：[QuickConnectManager](https://github.com/jellyfin/jellyfin/blob/v10.10.7/Emby.Server.Implementations/QuickConnect/QuickConnectManager.cs)、[QuickConnectController](https://github.com/jellyfin/jellyfin/blob/v10.10.7/Jellyfin.Api/Controllers/QuickConnectController.cs)、[UserController](https://github.com/jellyfin/jellyfin/blob/v10.10.7/Jellyfin.Api/Controllers/UserController.cs)。

**证据边界：** 此版本 `GetAuthorizedRequest()` 是读取而非读取后删除；不能据此宣称 Jellyfin 兑换严格一次性。授权后的时间更新与注释也不能简单推导成“一分钟兑换窗口”。本文只借鉴交互与双秘密分工；下文的原子单次兑换、限流和期限是 Javdex 建议，不冒充 Jellyfin 保证。

### 3.2 Plex TV linking：4 字符码，不是 Jellyfin 六位码

**来源事实：** Plex 大屏应用选择 Sign In 后显示 **4 字符** linking code。用户在电脑或手机访问 `https://plex.tv/link`，登录正确的 Plex 账号并提交码；播放器数秒后刷新并关联账号。部分平台提供二维码进入相应页面。[Plex 官方连接说明](https://support.plex.tv/articles/203395277-connect-app-to-your-plex-account/)

Plex 另提供 Authorized Devices 列表；同一物理设备的不同浏览器可能是不同条目，可查看并移除。[Plex 官方设备说明](https://support.plex.tv/articles/115007577087-devices/)

**证据边界：** 上述用户文档没有完整定义服务端秘密、轮询协议或 token 寿命，不能推出“码永不过期”，也不能据此认定 Plex 实现了 RFC 8628。

**项目建议：** 借鉴“大屏展示，小屏/桌面确认”和设备列表。Javdex 无需引入公网账号服务；第一阶段由 Electron 承担授权方。不同浏览器应视作不同登录实例，而非用物理设备名称自动互信。

### 3.3 OAuth RFC 8628：规范事实摘要

**来源事实：** RFC 8628 面向输入受限设备，并要求设备请求使用 TLS。关键要素如下（§3.1–3.5、§5）：

| 要素 | 标准含义 |
| --- | --- |
| `device_code` | 设备持有、用于轮询/领取 token 的高熵秘密，不展示给用户 |
| `user_code` | 人工确认的短码；长度不固定为六位，须配合限流 |
| `expires_in` | 两类码的有限寿命；规范没有统一有效分钟数 |
| `interval` | 最小轮询间隔；未提供时为 5 秒 |
| `authorization_pending` | 按间隔继续轮询 |
| `slow_down` | 本次及后续间隔增加 5 秒；连接超时也须降频 |
| 拒绝、过期及其他错误 | 停止轮询；过期后宜等待用户主动重新发起 |
| `verification_uri_complete` | 可携带 user_code 或等效信息，用 QR/NFC 传递；仍须显示短码并完成授权确认 |

扫码不替代授权者认证与确认；短码、设备秘密和最终 access token 是不同对象。来源：[RFC 8628 §3](https://www.rfc-editor.org/rfc/rfc8628.html#section-3)、[§3.3.1 二维码](https://www.rfc-editor.org/rfc/rfc8628.html#section-3.3.1)、[§5 安全考虑](https://www.rfc-editor.org/rfc/rfc8628.html#section-5)。

**项目判断：** 当前可以做受限 LAN 配对，但不能称为合规 OAuth device grant；完整引入 OAuth 授权服务器对当前单桌面、只读浏览场景收益有限。

### 3.4 Passkey / WebAuthn：HTTPS 和 RP ID 是两道门槛

**来源事实：** WebAuthn API 仅在 secure context 暴露。RP ID 是域名标识，不含 scheme、端口或路径；通常等于调用方有效域名或其可注册域后缀。创建与获取凭证算法拒绝以 IP 地址格式作为有效域名。服务端还须验证实际 Origin。[W3C WebAuthn Level 3 §5](https://www.w3.org/TR/webauthn-3/#sctn-api)、[创建算法](https://www.w3.org/TR/webauthn-3/#sctn-createCredential)、[获取算法](https://www.w3.org/TR/webauthn-3/#sctn-getAssertion)

Secure Contexts 将回环地址与符合解析要求的 `localhost` 视为 potentially trustworthy；普通私网地址不享有该例外。[W3C Secure Contexts §3.1](https://www.w3.org/TR/secure-contexts/#is-origin-trustworthy)

**对本项目的推论：**

| 地址情形 | 判断 |
| --- | --- |
| `http://192.168.x.x:端口` | 普通 LAN HTTP 不满足安全上下文条件，且 IP 字面量不满足标准 RP 域名要求 |
| `https://192.168.x.x:端口`，证书受信任 | 可解决传输信任，仍未解决 WebAuthn 的 IP 域名限制 |
| `http://localhost:端口` | 属于本机开发例外；手机上的 localhost 指手机自身，不是桌面服务器 |
| 稳定域名 + 无证书错误的 HTTPS | 具备评估前提，仍需校验 RP ID、Origin 和实际浏览器/认证器支持 |

自行点击忽略证书错误、要求用户打开浏览器实验开关，不能作为正常产品方案。Electron 自身的信任也不会传递给远端浏览器。给 LAN IP 配一个 HTTP 域名仍未解决 secure context；仅添加 TLS 也不会自动让现有 Host/Origin 校验接受域名反代。

**项目建议：** 后续采用稳定域名和各客户端受信任的 HTTPS，再设计 Passkey 注册、恢复与移除流程；不承诺所有电视浏览器支持。Passkey 验证身份后仍需应用会话，不能代替会话过期和撤销政策。

### 3.5 Trusted device：持久授权，不是设备天然可信

**来源事实：** Cookie 的 `Max-Age`/`Expires` 控制浏览器保存期限，浏览器仍可能提前清除；`HttpOnly` 限制脚本读取，`Secure` 约束安全传输。Cookie 不按端口隔离，明文 HTTP 的 Cookie 可被网络攻击者获取。[RFC 6265 §4.1.2](https://www.rfc-editor.org/rfc/rfc6265.html#section-4.1.2)、[§8](https://www.rfc-editor.org/rfc/rfc6265.html#section-8)

OWASP 要求服务端执行会话期限与失效，区分闲置、绝对期限和 token 更新，并强调退出时服务端撤销；它并未给所有产品规定统一的“可信设备 30/90 天”。[OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html#session-expiration)

**项目建议：** 将“可信设备”定义为用户明确批准的某个浏览器凭证。设备名、User-Agent、IP 只作为识别辅助，不能证明所有权；实际授权取决于可撤销的随机凭证。HTTP 下该凭证仍是可被窃取重放的 bearer credential，摘要存储和轮换无法补足传输保密。

## 4. 第一阶段建议：桌面批准六位码 + 有限期可信设备

以下全部是待讨论的 Javdex 设计，不是现有行为或实施授权。

### 4.1 建议交互与凭证边界

1. 用户在新 Web 设备主动点“与桌面配对”。服务端生成短期请求，返回六位数字码、到期时间与轮询间隔；另给该发起浏览器一个 32 字节随机配对秘密。页面展示可读的码，例如 `123 456`。
2. 用户在可信 Electron 桌面输入该码。桌面显示待配对客户端名称、来源地址、发起时间和“只读浏览与播放”范围，用户核对正在操作的设备后批准或拒绝。客户端提供的名称应明确只是辅助信息。
3. 原浏览器携带配对秘密查询状态。批准后通过受保护的兑换操作取得新会话；仅有显示码、请求 ID 或截图不能兑换。
4. 原子地完成“批准请求 → 已兑换”转移，不能并发兑换多个设备。配对秘密与码在完成、拒绝、取消或过期后失效；兑换响应丢失的恢复方案须另行设计，不能因此无限重复签发。
5. 用户可选择记住此浏览器；桌面可查看、命名和撤销该可信设备。公共/临时设备使用普通短期登录。密码入口保留作回退。

建议状态为 `pending → approved → consumed`；`denied / expired / cancelled` 是终态。所有时间和权限由服务端判断；服务重启清空未完成配对，但保留尚未到期、未被撤销的持久授权。

### 4.2 建议初始参数与防滥用

| 参数 | 建议初值（非标准规定） |
| --- | --- |
| 显示码 | 均匀随机六位数字，活跃集合内唯一；允许前导零可提供 100 万组合 |
| 配对秘密 | 32 字节随机值，与显示码独立；服务端保存摘要 |
| 请求有效期 | 创建起 5 分钟；批准不延长总期限 |
| 批准后兑换窗口 | 最多 60 秒，且不得超过请求原到期时间 |
| 轮询 | 5 秒起步；服务端强制节流，超时退避，到期停止 |
| 请求与尝试预算 | 同时限制每来源、每授权者和全局请求数；配对请求、查码、审批、轮询与兑换各自受限 |

六位码的空间只有约 20 bit（`log2(10^6)`），适合人工查找，不适合作为登录秘密。限流必须覆盖总体活跃请求，避免大量申请导致碰撞、扫描或桌面提示轰炸；具体预算需要设备数量与误输体验验证，不能照抄密码登录 limiter。

建议只在桌面主动打开配对管理时允许受理，或提供有期限的配对开关。查询、审批和兑换响应均禁缓存，秘密不进 URL、日志或分析事件；可使用仅服务端可读的临时 Cookie 保存配对秘密，继续保留 Origin 等来源检查。临时 Cookie 在 HTTP 下仍无传输保密能力。

### 4.3 持久登录与寿命：先解决跨重启，不暗中延长授权

第一阶段建议对明确选择记住的浏览器持久化凭证摘要、设备标识、批准时间、最近使用时间、绝对截止和撤销状态。**暂沿用闲置 24 小时、原始授权起绝对 7 天的上限**；这两个值是现有项目政策，不是行业安全认证结论。

为控制第一阶段复杂度，可将其做成可按设备管理的持久会话，而非立即叠加“长寿命 refresh token 自动重建短会话”。这样能跨重启恢复，但仍会在一天未使用或七天届满后要求重新配对/认证。可信设备记录可以保留供展示，记录存在本身不能继续授权。

- Cookie 与服务端记录须同时有效；重启、轮换 token、刷新页面都不能重置原始绝对截止。若重新设置 Cookie，其有效期不得超过剩余授权期限。
- 桌面撤销单台/全部设备要使其凭证立即不能再授权新请求。主动登出应撤销本浏览器的持久凭证，避免刚登出就自动登录。
- 普通重启与主动“撤销全部授权”应明确区分。密码重置、账号安全重置建议撤销关联授权；这需要将来明确产品语义，不能因持久化丢掉现有撤销能力。
- 撤销后的正在播放连接是否立即中断需要单独设计；现有鉴权发生于请求入口，不能承诺删除记录会中止已建立流，更无法收回已下载内容。

若后续需要数周免登录，可分离短期访问会话与长期设备凭证，但此时七天仅是子会话寿命，**有效免登录授权可能长于七天**。必须另设外层绝对授权截止，不能宣称每七天建新会话就仍保持七天总上限。

### 4.4 稳定访问地址是“记住设备”的另一前提

**来源事实与本地推论：** 当前 Cookie 没有 `Domain` 属性，按当前主机保存；服务器从一个 LAN IP 换到另一个 IP 时，浏览器不会把旧 Cookie 自动迁移给新地址。不同本机网卡地址也可能形成不同登录入口。反过来，仅改变端口并不能隔离 Cookie，因为 Cookie 不按端口划分。[RFC 6265 §5.3](https://www.rfc-editor.org/rfc/rfc6265.html#section-5.3)、[§8.5](https://www.rfc-editor.org/rfc/rfc6265.html#section-8.5)

**项目建议：** 第一阶段优先保持固定访问入口，可通过路由器 DHCP 地址保留减少变化；地址改变时提示重新配对，不用 URL 传递旧 token 来“迁移”。后续以稳定域名解决入口问题，但仍需配合 HTTPS 与明确的 Host/Origin 支持。服务端设备记录持久化本身无法让浏览器在新主机地址上自动获得旧凭证。

## 5. QR 与只读权限边界

**项目建议：** 第一阶段桌面显示的二维码可以仅包含 Web 首页地址，解决手机输入 IP 的麻烦；扫码后仍走配对。电视也应始终显示可手动读取的码，不强制扫码。

若未来引入手机 Web 审批，可让二维码包含本站审批地址和短期 user_code/等效请求定位信息；打开只展示确认页，不能 GET 即批准。授权者必须具备独立审批资格并明确确认，普通只读会话不能因“已登录”自动成为管理端。第一阶段不必提供这种 Web 审批入口。

| 能力 | 建议授权条件 |
| --- | --- |
| 创建配对 | 未登录也可申请，但仅在允许配对时，受来源与数量限制 |
| 查询/兑换 | 绑定发起浏览器的高熵秘密；兑换还需有效批准 |
| 批准/拒绝 | 第一阶段仅可信 Electron 管理通道；不是靠 LAN IP 或任意 Web Cookie |
| 将来的 Web 审批 | 显式独立审批权限、重新认证/确认与 CSRF 防护；单独设计 |
| 目录、详情、图片、播放 | 有效只读凭证 |
| 编辑媒体、删除、刮削、修改设置等 | 不因任何配对或认证端点例外而开放 |

**认证端点允许 POST 是为改变认证状态，不是开放媒体写权限。** 保持明确的认证端点白名单；不要将“只有 GET”机械地作为只读定义，也不要因新增审批而把其他 POST 放开。

## 6. HTTP 限制与分阶段路线

**当前限制的推论：** LAN 地址白名单与来源检查能约束访问面，但不加密网络流量。配对减少密码输入和密码传输；HTTP 中的配对秘密、登录 Cookie、响应内容仍可被有能力观察或篡改链路的攻击者窃取/修改。**第一阶段主要改善便捷性；不能把免输密码或记住设备宣传成传输安全提升。** 更长的持久令牌期限还会扩大失窃后的可用窗口。只读视频库仍有内容隐私，不能以“不能编辑”为由认定风险消失。HTTPS 后也应保留权限、期限与撤销机制。

| 阶段 | 建议范围 | 进入下一阶段前的条件 |
| --- | --- | --- |
| 0：本次研究 | 记录官方证据、限制与方案，合并本轮核验补充 | 另行决定是否立项 |
| 1：便捷配对 | 六位码、桌面批准、一次兑换、设备列表/撤销、有限期持久会话；保留密码 | 验证生命周期和只读边界；明确 HTTP 风险与寿命政策 |
| 2：可信传输 | 稳定域名与受信任 HTTPS；明确直连或可信反代的 Host/Origin/代理边界 | 不能靠盲信 `X-Forwarded-*` 绕过现有校验；验证目标电视证书兼容性 |
| 3：更长保持与 Passkey | 评估长期设备凭证、轮换/重放处置与 Passkey；保留大屏配对 | 明确外层授权截止、恢复方式、撤销语义及终端支持 |

第三阶段可讨论“设备授权闲置 7 天、绝对 30 天”等候选值，但它们是待评估政策，不能作为 HTTP 阶段的默认承诺。若采用类似 refresh token 的凭证，可参考轮换或发送者约束的抗重放思路；不要把本地 Cookie 方案直接称为 OAuth 合规实现。[RFC 9700 §4.14](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14)

## 7. 后续核查清单（不是本次执行任务）

- 后续若有更多独立核查结果，继续对照 secure context 与 RP ID 两道条件、内层会话与外层授权期限；当前结论不替代目标浏览器验证。
- 若另行批准实施，验证：过期/拒绝后不可兑换、并发只兑换一次、只有显示码不能登录、二维码不授予权限、普通只读账号不能批准新设备。
- 验证跨重启不重置寿命，闲置与绝对期限均生效，撤销和登出不能被自动续期绕过，播放流撤销边界符合说明。
- 验证旧 Host/Origin 与来源限制未被放宽，所有媒体编辑入口仍拒绝；手机、电视的 Cookie 保存和清除行为须实机验证。
