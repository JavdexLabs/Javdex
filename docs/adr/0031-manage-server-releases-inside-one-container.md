# 单容器运行外壳管理服务端发行包

用户确认只部署一个容器。采用常驻管理父进程监督非 root 业务子进程，通过签名的完整服务端发行包、持久版本目录和停机数据快照实现在线/离线更新；不安装宿主机助手、不挂载 Docker socket、不使用 Docker-in-Docker，也不让业务进程覆盖自身代码。此前未发布的 Docker 镜像更新执行器由该方案替代，不并行维护两套托管更新机制。

程序、查询 worker、Web 与对应 Linux 架构原生依赖作为一个发行单位；业务版本与运行外壳版本分离，固定在镜像中的管理器、Node 与系统环境仍通过替换镜像维护。数据迁移后验证、提交前恢复和提交后不覆盖新写入的原则保留。该取舍减少用户部署与宿主机权限负担，代价是增加进程监督、发行目录完整性及运行环境兼容验证；不是不停机热更新，也不把同容器进程隔离宣称为安全沙箱。

## 2026-10-15：镜像启动时升级业务

用户确认更换镜像也应带来对应业务升级。同运行环境内按 SemVer 比较镜像种子与当前发行，仅较新版本进入既有停机备份、安装、验证、持久提交与恢复事务；同版本和较旧种子不覆盖程序卷。信任来自管理员所选镜像，逐文件与原生闭包校验仍执行，不伪造签名清单、不开放未经签名的远程安装入口。下载和上传路径继续要求官方 Ed25519 签名。

安装记录显式区分镜像身份与签名包；本地持久摘要记录每个镜像发行的自动尝试，避免重启循环。保留管理员已上传/准备的更新，不自动抢占。首次空程序卷初始化不属于这项托管升级，已有旧资料须事先人工备份。此决策不引入额外联网发现，也不改变容器运行环境跨代迁移要求。

## 2026-10-15：统一地址与一次配对

新 Compose 通过 `JAVDEX_PUBLIC_URL` 启用常驻 HTTPS 网关；业务子进程仅监听容器回环，更新停服期间管理入口仍存活。网关覆盖转发头、传递真实对端，业务仅接受带进程级随机凭据的回环转发；转发请求不能使用部署侧恢复接口，网页 Cookie、writer 和更新 token 仍分离。未启用新配置的旧双端口部署保持原行为。

部署侧 `pair` / `pair-recover` 发放十分钟一次性配对信息，客户端同时保存统一地址、固定证书及两类授权。候选 writer 在领取前持久化，依赖既有 writer 事务回执支持丢响应重试；显式恢复才允许接管已有 writer。客户端只在固定证书校验后发送凭据，禁止跨 origin 和重定向。播放器使用受限回环流桥接访问授权媒体，固定服务端证书，不向播放器泄露管理凭据，不进行转码。浏览器仍需单独信任证书，统一入口不等于开放公网。
