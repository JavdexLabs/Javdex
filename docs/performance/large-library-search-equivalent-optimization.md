# 保持现有能力的搜索优化：PERF-11A 与 PERF-11B 评估

日期：2026-09-11。基准为本轮修改前的工作区，包含此前已接受的性能优化；不是官方 v0.6.2 二进制。本轮不增加搜索模式、不改变 schema，也不操作用户数据库。

## 已落地的变化

1. 桌面 scoped/legacy：先物化匹配演员 ID，再通过 `video_actress(actress_id)` 索引展开影片 ID。原名称类型、ownership 联结、名称归一化和 `an.name LIKE ?` 保持原样。`IN` 保持影片去重；代码/标题条件、三个参数、所有筛选与排序不变。
2. Web：独立保留 `main_name LIKE ? ESCAPE '\'`，仅预求值演员 ID。Web 仍只搜索主名，不因桌面实现而扩大到别名；`%`、`_`、反斜杠继续按原规则转义。
3. Web 非空搜索：一次求出 active 库中非隐藏成员的影片 ID。旧关联可见性子查询可能每部影片扫描 `is_hidden` 索引；新 `IN` 消除该重复扫描。指定 library 的附加过滤保留；跨库重复成员不产生重复结果。无关键词浏览和 collections 保持原 SQL。

界面、输入防抖、准确 total、页码、排序与返回行为不变。名称归属变更、演员改名、关联变更与可见性更新继续通过已有读修订缓存失效机制生效。未增加跨请求候选数组或新缓存。

## 测量方法与边界

- macOS arm64，Electron 内置原生 better-sqlite3，SQLite 3.53.4；所有 fixture 使用临时独立数据库。
- 桌面：300,382 影片、10,000 演员、600,764 关联，每部影片 128 字节合成简介。同一数据库比较本轮前/后仓库；分别测 `ANALYZE` 后和无 `ANALYZE`。
- 单库与 all scope（一个 active 库）各测一轮。表中为单库；完整原始数据包含两个 scope。
- 每个查询三次样本，前后交替，每次未命中测量前写入独立探针表使修订缓存失效。表中是中位数，不是 p95，不是冷盘。
- Web：10,000 影片、1,000 演员、20,000 关联，约七分之一成员隐藏，无 `ANALYZE`。使用同一数据库上的旧/新 reader；三次交替，逐次对照完整返回值。
- 只测同步数据库查询，不含防抖、IPC、HTTP、渲染或图片。基准期间部分检查曾并行运行，细小百分比差异不作为收益证据。
- Web 最初的 30 万对照长时间未完成，已中止；没有采用其耗时。Web 表格只代表明确完成的 1 万 fixture，不外推成 30 万库效果。

## 桌面结果（毫秒，准确 count + 60 条页）

| 查询 / 命中量 | 无统计：修改前 | 无统计：修改后 | 有统计：修改前 | 有统计：修改后 |
|---|---:|---:|---:|---:|
| `ABC-123456` / 1 | 324.21 | 78.92 | 73.94 | 74.10 |
| `中文作品 123` / 1,111 | 327.80 | 85.50 | 79.81 | 79.30 |
| `Actor00001` / 61 | 322.66 | 78.09 | 72.60 | 72.94 |
| `不存在` / 0 | 307.65 | 74.15 | 72.62 | 73.27 |
| `Actor` / 300,382 | 1,023.26 | 544.25 | 557.18 | 542.51 |

无统计信息时常见查询约改善 3.8–4.2 倍；有统计信息时优化器原本已能采用较好的执行顺序，常见查询基本不变。不能宣称所有搜索都提升四倍。

确定性回归：1,000 部影片共享一个演员，无 ANALYZE；原 scoped count+page 归一化调用 **2,000 次**，新实现 **2 次**，总数及页 ID 相同。正式测试还调用真实 `normalizeActressName`，同时验证 scoped 和 legacy；不使用容易受机器波动影响的毫秒断言。

## 候选 ID 方案的选择

scoped 查询此前已经通过 `WITH page AS MATERIALIZED` 先分页 ID，再读取当页详情。本轮没有重复实现这一层。

实验把番号、标题和演员三路全部改成 `UNION` 影片 ID：有统计单库中，普通关键词约 73–80ms 变为 79–86ms；`中` 从 106ms 变为 337ms；`%` 从 90ms 变为 629ms。额外扫描和集合去重不值得，**不采用该实验**。

Web 的可见成员 ID 则是另一种候选集合：它替代逐影片重复计算的权限存在性检查，保留原过滤含义，并有实际收益，因此采用。

## Web 结果（毫秒，准确 count + 36 条页）

| 查询 / 命中量 | 修改前 | 演员 + 可见性预求值后 |
|---|---:|---:|
| `中文作品 123` / 9 | 1,873.00 | 3.41 |
| `Actor00001` / 17 | 1,875.50 | 3.33 |
| `%`（字面量） / 17 | 1,889.81 | 3.26 |
| `Actor` / 8,572 | 884.70 | 14.75 |
| `不存在` / 0 | 1,890.51 | 3.21 |

不要把 Web 的巨大收益全部归因于演员名称重复判断：执行计划显示旧可见性检查使用 `idx_library_video_memberships_recent(is_hidden=?)`，没有以 video_id 定位。只预求值演员时，稀疏搜索能提前排除影片，宽泛 `Actor` 仍约 1 秒；追加可见 ID 预求值后才消除了这个扫描成本。保留了中间实验数据与最终 EQP 供核查。

## 正确性与验证

- 桌面固定旧谓词 oracle：主名/别名/中英文与罗马字类型，排除类型，缺失/错误归属，多演员重复命中，Unicode、全角、大小写、空白、`%/_/\\`；ANALYZE 前后对照。
- scoped/legacy 的 total、ID 顺序、正反向页边界；标签交集、演员、年份、评分、刮削状态；跨库、隐藏、归档；`code/add_time/release_date/rating` 双向排序，日期空值及同值。
- Web 固定旧可见性和旧演员谓词 oracle：全局及指定 active/archived 库、隐藏-only/归档-only/无成员、重复成员、某库隐藏但另一库可见；名称主名与字面通配符，全部四种排序和分页。断言旧 SQL 的两段替换确实执行，避免新查询自我对照。
- 已有 worker、WAL 快照、写入失效、业务查询等测试继续覆盖集成路径；前端已归档文件哈希保持不变。
- 最终测试、构建及源码哈希见 [验收清单](large-library-results/search-equivalent/manifest.json)。

## PERF-11B 决策

**本轮暂缓 trigram/schema 迁移。** 已验证的主要退化首先来自重复演员/可见性判断；本轮可以在不迁移数据库的条件下改善这些路径。有统计的桌面常见搜索已约 73–80ms，当前证据不足以证明新增索引、回填、写放大和恢复机制值得立即上线。

剩余风险没有关闭：桌面命中整库的演员查询仍约 0.54s；极多无关联演员时预求值会检查更多演员；多 active 库的性能、Windows/HDD/冷盘与真实名称分布尚未测量。宽泛命中的关系展开、准确总数、排序与深 OFFSET 不能指望 trigram 自动解决。

后续触发条件：在目标库上分开记录 count/page 和执行计划，确认重复关联已消除后，低命中长子串的文本扫描仍主导延迟，再实施 PERF-11B。届时保持现有 LIKE 为语义基准，索引候选必须不漏结果，最终原条件复核；短词、特殊模式、未 ready/失败索引走原查询。正式回填和写入同步按计划第 5 节实现，不使用 MATCH 替换现有包含搜索。
