# issue #100：当前搜索与 v0.6.2 对照

2026-09-11。GitHub Latest仍为v0.6.2（标签提交`dc6f2d25a8fadd7144e6a36d6e9141942e8c4be5`）。[issue #100](https://github.com/JavdexLabs/Javdex/issues/100)描述Windows x64、300,382影片、约1GB数据库，搜索约1.3秒；其中用户修改后的耗时是用户报告，不能直接当作本机官方版本对照结果。

## 结论

当前未发布工作区已经优化搜索所在的列表路径、重复读取和界面响应，但没有完成核心子串搜索算法优化。尤其不能把worker隔离或缓存命中的收益描述为所有新关键词都能毫秒级返回。

- `scopedVideoCatalogRepo`消除了多余DISTINCT，先选本页ID再补完整投影；只有一个活动库时，全局scope短路到单库。
- count与页面分开缓存，同筛选翻页/换排序可以复用count；写入/外部提交/schema变化失效。
- 桌面列表及首页/全局搜索经只读worker执行；renderer窗口限制历史卡片保留，降低长时间浏览的累积负担。
- **核心搜索条件未变**：番号/片名仍为`LIKE '%词%'`；演员搜索仍为影片侧IN子查询及内部按演员关联的EXISTS/名称归一化。`actressSearchSql.ts`与v0.6.2没有差异；不能把现状简化成每部影片都重新执行整个演员子查询。
- 尚无正式FTS/trigram索引，也未接入搜索框的独立精确番号快捷路径或演员候选预求值。新关键词、短词、冷盘及多库复杂搜索仍需后续PERF-11/12专项优化。

## 本次同库实测

临时合成数据库：300,382影片、10,000演员、600,764条影片演员关系，128字节简介，无真实媒体/封面。macOS arm64，SQLite3.53.4，执行ANALYZE；双方使用**同一个当前初始化schema数据库**。抽取v0.6.2的scoped仓储源码并复用当前共享依赖，对比当前仓储，属于查询实现对照，不是两套完整应用二进制的验收。

每个查询预热后分别运行3次，中位数如下。旧/新调用顺序交替；每次非缓存测量前提交不改变业务数据的独立表写入，使当前缓存失效。每次比较返回完整业务字段及total完全一致；连接修订不纳入业务字段。时间仅包含仓储调用，不包含造库、结果断言、IPC、渲染或图片。
