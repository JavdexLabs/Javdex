# macOS CPU 私有帧通道实测

状态：2026-10-27 按用户确认正式采用，作为 Mac CPU 兼容模式及自动回退进入 CPU 后的正常实现，无需实验开关。采用范围仅为 Mac；继续默认 GPU。下述 4K 工作集增长作为本次性能取舍保留，后续内存优化独立实测。

2026-10-27，Mac CPU 播放采用隔离宿主直达 preload 的私有 MessagePort，保留原生 64 字节行对齐、复用 scratch 和输出复制；VideoFrame 使用复制输入。审查修复前的 M4 开发构建配对采样中，1080p60 和 4K24 的应用进程合计 CPU 成本分别下降约 23% 和 18%，4K 工作集增加约 195MiB。提交前另修复两项回收时序问题，最终源码的复核单独记录，不将上述旧源码数字直接充作最终构建的测量。

默认 GPU、实际输出尺寸、帧率、色彩和缩放策略保持。Windows 的复制到 Canvas、Linux 的 memfd／ACK 和 video 输入策略没有迁移到新端口；原生 C++ 没有修改。当前合同见 [内置播放](../BUILTIN_PLAYBACK.md)，结构化结果与逐文件摘要见[实测数据](macos-cpu-private-frame-channel-2026-10-27.json)。

## 采样口径和结果

基线为 `9e73fe7187afad87a5e6b51902fa884e994e56f1`，本节候选为其上的审查修复前工作区源码，不能将基线 SHA 当作候选的完整身份。两套隔离应用使用相同的正常原生 addon，SHA-256 为 `6c970dd5f0005350265b88ac7f8ed57d311f2c6b3a63e05c6023728770d0d7fc`。候选的源码、编译入口及原始报告摘要另存于实测数据；提交前修复后的身份与结果位于其中独立的 `postReview` 记录。

设备为 Apple M4、10 个逻辑核、16GiB 内存，Electron 44.9.3／Chromium 152.0.7977.167。使用合成 H.264 SDR 素材和可见窗口，每种负载按“基线、候选、候选、基线”运行两组 20 秒采样，表中为各自均值。CPU 以一个逻辑核满载为 100%，统计应用进程树，下降比例为相对变化，不是整机占用百分点。内存为各进程工作集合计，共享页可能重复计入，不等于独占物理内存。

候选另完成 120 秒 60fps 播放：实际 video 59.99fps、播放位置推进 119.90 秒、mpv／video 丢帧均为零，CPU 合计约 210.2%，工作集合计约 1074.2MiB。此前原型配对中候选一次出现 1 个 mpv 丢帧，基线长播也出现 1 个；这些记录保留，不据最终零丢帧样本宣称已定位或消除所有偶发丢帧。

## 通道和内存选择

主进程继续认证主 frame 的 surface／binding，校验帧尺寸、序号和时间线，并管理调度及最多两帧复制信用额度。像素从隔离宿主直接发送到 preload；主进程不再序列化和中转全帧像素。每次绑定分配独立通道代，旧绑定的像素、完成和关闭回调不能操作新绑定。

preload 有界配对元数据与像素，不依赖两路消息的到达顺序。新时间线的像素可以先于控制 flush 到达，必须保留到对应时间线生效；旧时间线、退休帧和解绑时的待消费输入按原信用规则清理。VideoFrame 完成后关闭帧并归还复制信用，GPU 槽位仍采用原有真实 GPU 释放与 `allReferencesReleased` 条件。

早期“直达端口＋转移紧密输入”在 4K 下工作集偏高，保留原生输出复制仍不能消除此差异。当前选择对 VideoFrame 复制输入，降低这一方案的工作集，但最终正常 addon 的配对结果仍高于基线约 195MiB。诊断中的等待队列最多两帧，4K 像素约 63.3MiB；没有发现等待队列无界增长，这不能单独证明浏览器内部内存原因。停止后手动 GC 只用于诊断，没有加入生产逻辑。额外分离 ArrayBuffer 的试验工作集更差，未采用。

## 验证和失败边界

- 源码合同回归 131 项通过、零失败、零跳过，覆盖两路先后顺序、未来时间线 flush、退休帧、重绑、旧回调、两帧上界、端口故障、复制输入所有权及 Windows 原路径校验。Node 类型检查、改动文件 lint 和桌面生产构建通过。
- 实际候选应用完成 20 项操作：连续和突发跳转、三种尺寸、暂停继续、底栏／展开／全屏、三次停止重开，以及 CPU 宿主退出后的受控错误。停止后的宿主和排队帧归零，应用正常退出。
- 主动关闭仍在使用的私有像素端口，约 5.47 秒进入 `FRAME_CHANNEL_FAILED`，CPU 宿主退出，没有重新启动 GPU。首次脚本误要求用户文案包含 CPU，实际受控错误正确但断言失败；修正为验证结构化故障来源后复测通过，失败原报告保留。
- 禁用 Chromium GPU 后 video 仍输出正确画面、可控制并正常停止；4 秒样本产帧约 23.95fps、零新增丢帧，但位置只推进 3.75 秒，`realtime=false`，不记实时性门槛通过。
- 正常默认路径仍为 GPU／VideoToolbox，实际原生、提交和 video 节奏约 23.97fps。真实终止 GPU 隔离宿主后自动恢复 CPU video，保留进度、音量 31、静音和 1.25 倍速；全屏为实际 3840×2160，停止后 GPU／CPU 宿主均退出。

本轮为单台 M4 上的源码开发构建与合成素材验证，使用隔离验收资料目录和显式无钥匙串测试入口；正常凭据读取逻辑保持。结果不覆盖 Intel Mac、Windows／Linux 实机、签名安装包、物理 HDR、人工听音或独立公开软件产物验收。

## 提交前检视与修复

规范轴与需求轴各发现一项 P2，均已用回归复现并修复：

- 较新帧退休时，水位会清理较早的待配对帧；这些帧的复制信用额度必须一并归还，晚于水位到达的元数据也须归还，避免两帧通道退化。
- 主进程 IPC 的退休通知可能落后于私有端口的新像素，造成遵守生产额度的正常跳转被误判队列溢出。现在由隔离宿主在同一私有像素端口先发退休标记，再归还可生产额度；重复归还不重复发标记，正常解绑和意外端口故障仍分别处理。

新增真实宿主入口与 preload 接收器的联动回归，主动延迟元数据／flush、先交付旧像素，再释放旧帧生产替换帧。修复后替换帧可正常消费，待配对队列保持有界。最终相关合同回归 134 项通过、零失败、零跳过，Node 类型、修改文件 lint、桌面构建通过。需求轴针对实际修复再次只读检视，未发现剩余缺口。

最终构建另与同一原生 addon 的原基线各做一组 20 秒对照；这一轮样本数更少，独立保留，不与前面的两组均值混算：

| 实际输出 | 基线 CPU | 最终 CPU | 相对下降 | 基线工作集 | 最终工作集 | 工作集变化 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 2070×1060，60fps | 257.2% | 225.0% | 12.5% | 1061.1MiB | 1093.2MiB | +32.1MiB |
| 3840×2160，24fps | 308.9% | 253.7% | 17.9% | 1654.4MiB | 1759.0MiB | +104.7MiB |

四次对照均保持目标帧率、mpv／video 零新增丢帧，固定色块两种取像比较仍为零差异。两轮结果说明 CPU 收益和内存代价会波动，不能将某一次下降比例或工作集差值承诺为所有播放的固定结果。

最终构建又完成 60 秒 4K24：video 24.01fps，播放位置推进 60.08 秒，mpv／video 零新增丢帧；工作集均值约 1746.6MiB，前十秒／后十秒均值为 1855.4／1735.9MiB，区间 1647.4～1900.8MiB，停止后合计降至约 894.0MiB，1565 个构造帧全部关闭。该样本未见持续增长，不能据此宣称任意长时间无泄漏。最终构建的 20 项跳转、重开及宿主故障操作，以及真实 GPU 宿主退出后的 CPU video 接管均再次通过，应用正常停止与退出。
