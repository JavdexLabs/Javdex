# Windows CPU 原生缓冲区与分段计时

2026-10-27，在前一轮 Windows video／私有帧通道工作区上实现并验证。验收时为未提交开发改动，默认缩放、输出视口、软件解码、视频合成和 GPU 故障后的 CPU 接管保持原规则。

## 实现

Windows 的 libmpv 软件渲染直接写入 JavaScript 持有的独立输出缓冲区，不再先绘制到原生 scratch，再使用 `napi_create_buffer_copy` 做一次整帧复制。输出分配额外 63 字节，创建 64 字节对齐的 `Uint8Array` 视图；不循环复用已发布缓冲区，内存由 JavaScript／垃圾回收管理，CPU 帧生产仍受原有两帧信用额度约束。

libmpv 的 `rgb0` 格式明确不保证第四字节已初始化，因此输出前继续设置为不透明，并清理每行填充。Windows x64 使用 SSE2 批量设置第四字节，Windows ARM64 保留逐像素处理；视图前后的对齐字节也清零，因为跨进程序列化可能复制整个底层 ArrayBuffer。这样移除独立整帧复制，不能声称整个链路零拷贝：私有 MessagePort 和 `VideoFrame` 仍复制像素。macOS 保留原有 scratch 和复制策略。

`JAVDEX_PLAYBACK_DIAGNOSTICS=1` 开启 Windows CPU 分段统计：原生记录输出分配、软件绘制、像素整理和输出复制；utility/preload 记录像素 `postMessage` 执行、跨进程到元数据配对完成、VideoFrame 构造、写入等待及观察等待。主进程每 30 帧输出 `[playback-cpu-timings]` 聚合；原生数据通过现有私有 host statistics 读取。跨帧阶段可以重叠，投递时间包括主进程元数据路径及跨时钟校准误差，观察等待只计写入之后剩余等待；这些数不能相加当作端到端延迟。软件绘制包含 libmpv 更新／转换／缩放／字幕等工作，不单独代表异步解码时间。

## 配对测试

i5-12600K、Windows x64、Electron 44.9.3，使用两个只差原生缓冲区实现的隔离开发构建，二者均启用相同诊断。采用先旧、再新、新、旧顺序，各运行两次；每次预热约 3 秒，采样 16 秒。合成 H.264 素材与上轮一致，原生输出尺寸和窗口状态稳定，采样后截图有画面。帧率为 `requestVideoFrameCallback` 观测，不代表物理扫描；系统 CPU 占用在样本间约 43%–64%，样本短且存在背景负载波动。

| 素材／输出 | 原生复制前 | 直接输出后 | 前／后回调间隔 P95 |
| --- | ---: | ---: | ---: |
| 1080p60／1962×1065 | 27.7 fps | 30.5 fps | 55.6／45.8 ms |
| 4K24／3842×2162 | 7.47 fps | 7.39 fps | 182.6／180.6 ms |

1080p 的样本均值提高约 10%，不能承诺所有机器或影片均有相同收益。4K 两组基本持平，仍明显卡顿；两次直接输出样本分别为 7.26／7.51 fps，旧版为 7.42／7.53 fps。进程工作集合计在 1080p 前／后约 1284／1279 MiB、4K 约 2151／2093 MiB；包含可能重复计算的共享页，不能解释为独占内存变化。

同组样本内的阶段均值如下，单位为每个被统计帧的毫秒，取两次运行均值：

| 阶段 | 1080p 前／后 | 4K 前／后 | 含义 |
| --- | ---: | ---: | --- |
| 原生输出分配 | 约 0／0.38 | 约 0／4.29 | 旧版复用 scratch，新版每帧分配输出 |
| libmpv 软件绘制 | 23.0／22.4 | 70.9／80.5 | 包含软件绘制调用及附近调度；不是单独的解码计时 |
| 不透明通道／行尾整理 | 1.68／1.36 | 10.69／12.34 | 4K 的差异也受内存与系统负载影响 |
| 原生整帧复制 | 2.59／无 | 18.02／无 | 新版直接绘制，删除此步骤 |
| 像素端口 `postMessage` | 8.19／7.98 | 33.27／36.36 | 同步执行墙钟时间 |
| 后续投递与配对 | 13.72／12.93 | 69.36／77.89 | 并发路径，不是单独纯 IPC 或可相加项 |
| VideoFrame 构造 | 2.28／2.15 | 11.37／10.31 | 包含输入复制 |
| 写入／后续观察等待 | 0.08／0.07、1.27／1.45 | 0.11／0.10、2.27／2.07 | 只计各 await 的实际等待 |

4K 样本表明，虽然原生复制消失，新分配及软件绘制成本、像素 IPC 和 VideoFrame 输入复制仍较高；等待 video 回调并非此测量中最大的单项。不能仅依据这组并发计时确定单一瓶颈或宣称新的分配方式普遍更快。

## 验证与限制

预加载／帧通道测试 94 项、宿主／桥接测试 56 项通过，Node 类型检查、定向 ESLint 和原生构建测试通过。Windows 原生实测覆盖 4K 输出、大小边界、alpha／行尾及视图前后清零、不同帧缓冲区独立、重设尺寸和关闭后旧帧与克隆像素保持有效。

独立构建的六组可见窗口验收覆盖 1080p／4K、软件界面、真实私有端口关闭、连续跳转、SDR／HDR 五类色彩、GPU 宿主故障后的 CPU 接管和 ASS／PGS 字幕；均通过并正常退出。主进程观察到的像素载荷仍为零。当前标准开发运行库重新构建后，另运行同一原生测试与 CPU 私有通道真实窗口检查；代码段与独立验收二进制相同，整文件摘要因链接时间戳不同而不同。

原始计时、报告、诊断日志及两套隔离构建位于 `out/windows-cpu-optimization-20261027/`。本机结果不覆盖 Windows ARM64、其他显卡／驱动、用户实际影片、长时内存稳定性、物理显示扫描或新的签名安装包；未重新进行 Mac／Linux 原生窗口验收。
