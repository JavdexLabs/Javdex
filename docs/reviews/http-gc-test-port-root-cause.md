# HTTP / GC 测试提前失败的根因（2026-10-17）

## 失败路径

此前完整 Electron 回归中，`serverEnvironmentClient.test.ts` 的 GC 子进程在约 687 ms 后失败：预期“查询超时”，实际为“连接或 HTTPS 证书校验失败”。这个时间短于 5 秒请求期限，因此不能把它视为超时取消本身失效，复跑成功也不能证明问题已消失。

本机 Windows 的 TCP 动态端口范围为 1024–15000（`netsh int ipv4 show dynamicport tcp`），包括 Fetch Standard 禁用的 4045、6000 等端口。旧夹具使用 `server.listen(0)`，操作系统可以分配这些端口；Fetch 在发出 HTTP 请求前直接拒绝，底层错误为 `TypeError: fetch failed`，`cause: Error: bad port`。生产查询将底层连接错误转换为通用连接失败提示，于是触发“应该超时”的测试断言。

原始首次失败日志未记录监听端口和底层 cause，无法恢复当时的具体端口。后续没有改动宿主端口配置，循环实际 `listen(0)` 在第 79 次自然获得 4045，捕获上述错误链、相同断言失败，以及服务端请求数为 0。另将旧夹具固定到 6000，稳定触发同一路径。此次确认的是这个可重现的测试设计缺陷，不声称恢复了原失败那一次的全部现场。

## 修复与证据

测试夹具改用 `scripts/test-http.ts`，直接绑定 49152–65535 的随机端口并持有该套接字；仅对 `EADDRINUSE` / `EACCES` 有限重选，不先探测再释放端口，也不依赖 undici 私有端口表。该范围避开当前 Fetch 禁用端口。

新增回归通过真实监听占用制造首次 `EADDRINUSE`，确认重选后真实 Fetch 请求可达。GC 子进程增加请求数与 GC 次数断言，失败时输出端口和计数，仍检查对端连接关闭；生产 5 秒期限、测试 7 秒兜底、6.5 秒完成断言、1 秒关连接断言及子进程 10 秒限制均不变。

Linux 容器复核还暴露了另一个夹具问题：从 Windows 只读挂载目录冷加载 TS 子进程可能耗尽外层 10 秒预算。现在先在父测试中将真实查询实现及端口工具编译到本地临时目录，子进程直接执行该文件；没有替换 Fetch、HTTP 服务、GC 或查询实现，也没有增加任何超时限制。这样外层限制覆盖实际执行，而不包含跨文件系统的 TS 加载成本。

在相同“将所有端口 0 分配强制变成 6000”的受控干扰下：旧版请求数 0 并报 `bad port`；新版直接绑定到 50739，请求数 1、执行 82 次真实 GC，最终按原期限超时且关闭连接。因而修复验证包含确定性故障对照，并非只依靠重复运行转绿。详细现场保留于忽略目录 `output/http-gc-root-cause/{forced,natural,fixed}.json`。

## 验证边界

本机 Windows 的 Electron 43.4.1 / Node 24.18.1 与普通 Node 22.22.1 执行同一 HTTP 测试。最新 HTTP 与升级页回归 76 项通过，Node 网关／HTTP 组合回归 57 项通过。Linux Node 22.23.3 容器中更新器整套 149 项全部通过，覆盖真实目录 fsync、进程退出与此次 GC 用例。此修复只涉及测试端口分配与执行夹具，不修改生产 HTTP、GC 或超时取消逻辑；容器源码测试不代表生产镜像安装、实际升级或 macOS GUI 验收。
