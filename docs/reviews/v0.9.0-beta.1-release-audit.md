## CI 失败与定向修复

### 第一次：Windows 物理路径断言

首次 run 的源码为 `f91d26500cf54ca96b3f5e9c1bb80648955e38c6`。Windows Electron 全量测试第一批为 2509 项：2484 通过、1 失败、24 跳过。唯一失败为 `playbackSource.test.ts` 中手动导入文件的物理身份断言：实现使用 `fs.realpathSync.native`，得到 `C:\Users\runneradmin\…`；测试使用 JS `fs.realpathSync`，保留了同一目录的 Windows 8.3 别名 `C:\Users\RUNNER~1\…`。解析和首次验证已成功，失败发生在两种路径文本的严格比较，不是播放授权或文件读取异常。后续打包、服务镜像和发布作业均被跳过。

修复仅将该断言改为校验 native canonical path，并补充 Windows 别名说明；生产实现、文件替换／缺失、续播身份隔离等断言全部保持。现有测试就是实际 Windows 故障的回归入口，未新增替代性 mock 或跳过条件。macOS 不能产生该 Windows 8.3 临时目录差异，以下本地结果只证明修复没有引入本机回归，最终仍须新 run 的 Windows 全量测试通过：

- `node scripts/run-electron-tests.mjs apps/desktop/src/main/player/playbackSource.test.ts`：修复前后均 11 通过、0 失败、0 跳过。
- 同入口运行 `playbackSource`、`playbackResumeStore`、`playbackSession`、`recentPlayback`、`libmpvPlayback`、`playbackDisplay`、`playbackFailure` 七个测试文件：83 通过、0 失败、0 跳过。
- 变更文件 ESLint、`npm run typecheck:node`、`git diff --check` 通过。

### 第二次：单容器烟测入口编译

第二次 run 于 2026-10-13 15:46:56 UTC 从 `bd44c12cd0dbf2c5fabfc2a985a9020e046af3d5` 启动。Windows 全量测试、Windows／macOS／Linux 打包、打包后的 Agent 运行时验证和 macOS 签名检查均通过；amd64／arm64 的签名配置、服务端构建和更新专项测试也通过。两种架构均在 `npm run server:updater:smoke` 启动时失败：根包为 CommonJS，tsx 对 `.ts` 入口使用 CJS 转换，而 `server-updater-smoke.ts` 有 13 处顶层 `await`。脚本尚未执行平台检查或 Docker 命令，故不是架构原生依赖或容器升级故障；后续基础容器烟测、镜像上传、版本镜像索引和 Release 全部跳过。
