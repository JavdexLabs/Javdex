## 实际发布时的门禁

1. 审核最终 diff，完成提交和推送；核对源码、应用版本、升级说明与工作流输入一致，将 Changelog 的“发布准备”改成真实发布日期。
2. 用户授权正式发布后，以该提交运行 Release：`release_tag=v0.9.0`、`prerelease=false`、`verify_only=false`。不得复用历史构建产物；发布前先检查同名标签、镜像或 Release 是否已存在。
3. 四个原生 runner 完成固定源码构建、包内加载/PCM EOF、六个最终安装文件的实际提取/安装/挂载及来源回执，macOS 签名通过；汇总源码的四平台映射、原生快照/SDK与恢复检查通过。
4. Linux amd64/arm64 均通过真实单容器更新与基础烟测，再发布对应镜像和签名完整 `.javdex-update`。业务归档不能更新旧镜像内的管理器，0.8.0 首次升级须更换基础镜像并增加 `/program`。
5. 核验恰好 10 个自定义附件、九条唯一 SHA256SUMS 记录与全部下载字节；总源码及两个升级文件的签名、内层闭包、架构、版本、schema 和程序提交匹配。官方可信公钥保持不变。
6. 发布后确认非 Draft、非 Prerelease，标签和镜像对应最终程序提交；GitHub releases/latest、桌面正式更新提醒与官网指向 0.9.0。镜像使用固定版本标签，不创建滚动 latest；是否合入 main 按实际发布授权执行并记录结果。
