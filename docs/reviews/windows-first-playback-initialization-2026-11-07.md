# Windows 首次播放初始化等待修复

日期：2026-11-07。源码基线：`74feb6a1` 加本次未提交修复；版本保持 `0.9.2-beta.1`，未发布。

## 问题与处理

本机原包 GPU 宿主尚未发送 `ready` 就触发 `HELPER_HEARTBEAT_TIMEOUT`。Defender 记录同一宿主进程打开 `libmpv-2.dll` 的检查耗时 10.87 秒；独立加载播放模块最终耗时 34.58 秒，不需要打开媒体或创建 GPU 上下文。原有 5 秒运行心跳、影片打开和画面自检计时会提前终止这些初始化工作。

Windows/macOS 共用隔离宿主现在区分模块 `ready` 和渲染上下文 `initialized`。初始化上限为 60 秒，就绪后恢复原有 5 秒运行心跳。私有 `initializing` 状态让会话的 30 秒影片打开预算、接收器等待、色块自检和 CPU 恢复预算避开初始化。晚到消息不能绕过初始化上限，停止后的回调不能复活宿主。初始化超时采用独立故障代码，自动模式仍最多接管到 CPU 一次；显式 GPU 模式报告错误，CPU 故障不循环重试。

主进程首次同步加载互操作模块仍可能受系统文件检查阻塞，无法由 JavaScript 定时器抢占；本次排除了这段等待对影片打开计时的影响，没有调整安全软件设置、原生渲染、默认缩放或输出尺寸。Linux 继续沿用其独立 helper，本次未修改 Linux 宿主协议。

## 验证

在本机 RTX 4080、Windows、Electron 44.9.3 上，以新包的 `dist/win-unpacked/Javdex.exe` 验证同一部 NAS H.264 1080p/29.97fps 影片。使用独立资料库、静音、默认窗口，不截图；人工等待仅注入测试进程入口，没有进入产品包。

| 场景 | 结果 |
| --- | --- |
| 正常 GPU 播放 | 约 2.99 秒观察到播放，RTX 4080 / d3d11va |
| 播放中暂停 GPU 宿主 | 约 5.73 秒恢复 CPU，原因 `HELPER_HEARTBEAT_TIMEOUT` |
| GPU 宿主初始化前人工等待 35 秒 | 约 38.48 秒进入 GPU 播放，未提前超时、未回退 |
| GPU 宿主初始化前人工等待 65 秒 | 达到 60 秒上限，约 62.89 秒进入 CPU 播放，原因 `HELPER_INITIALIZATION_TIMEOUT` |
| 播放控制与关闭 | 上述场景暂停、暂停跳转、继续和停止通过；测试进程正常退出，无强制关闭 |

额外保留新包目录首次加载的真实超时记录：GPU 初始化达到 60.014 秒上限后接管 CPU，CPU 初始化约 12.39 秒，约 82.18 秒观察到播放。该轮脚本因预期 GPU 而标记失败，没有计作正常 GPU 通过证据；它说明极慢的系统检查仍可能触发有界回退，修复不保证每次冷启动都选择 GPU。随后独立执行上述通过场景。

类型检查通过。相关 Electron 回归 304 项通过，后续新增的两项延迟定时器边界另随宿主测试通过（该文件共 35 项）。覆盖慢初始化、初始化上限、运行心跳、画面自检、媒体打开预算、CPU 恢复、停止与迟到消息，以及现有控制／租约行为。

本机证据保留于忽略目录 `out/windows-first-playback-fix-20261107/`：`verified/normal-runtime-stall.json`、`acceptance/slow-init.json`、`acceptance/init-timeout.json`、相应日志、类型检查和回归输出。一次未实际注入延迟的测试脚本失败记录也保留，未用作慢加载通过证据。
