---
title: "服务端配对与客户端更新"
description: "Javdex 0.9.0 · 服务端配对与客户端更新"
---

首次启动自动生成 TLS 证书和随机更新凭据，不在日志输出秘密。管理员获取配对 JSON：

```bash
docker compose -f docker-compose.example.yml exec javdex node /opt/javdex-manager/index.js pair --config /config/server.json
```

使用新 Compose 示例的统一地址部署，在桌面“设置 → 存储与导出 → 资料库连接”的一次性配对输入框粘贴该 JSON，点击“配对并保存连接”后重启。地址、证书和两类授权一次保存。首次配对要求桌面与业务同版本，且系统安全存储可用；信息有效期 10 分钟，失效须重新生成。同一电脑网络中断可用原信息继续领取，不能由另一电脑重复领取。

添加电脑：管理员重新运行 `pair`，在新增电脑完成相同操作；已有设备继续可用。所有可信电脑拥有相同管理权限，共享收藏、清单与资料；最近播放与续播仍按已有本机规则保存，不引入个人账号。

撤销电脑：在任一已连接桌面的“资料库连接 → 可信设备”撤销其他电脑，立即停止其管理、授权播放和更新访问。当前电脑须由另一台撤销。维护任务进行中先完成或取消任务；其他电脑会刷新授权代次，未完成的传输可能需要重试。同一资料被其他电脑修改后会提示冲突，刷新再编辑，不自动覆盖。

全部设备遗失时：管理员将 `pair` 改为 `pair-recover`，完成新配对后撤销所有旧设备及其播放／更新授权。地址或证书变化后也需重新配对，不会自动信任新证书。

桌面核对证书指纹、serverId/catalogId，设备管理凭据仅在主进程通过系统安全存储保存，并绑定原地址。统一入口按同一可信设备凭据授权业务与更新，网页 Cookie 不授权这两类操作；更新协议独立于业务版本，普通资料管理仍要求同版本。

旧双端口部署（未设置 `JAVDEX_PUBLIC_URL`）仍使用独立流程：`pair` 输出旧更新配对 JSON，填入“服务端更新 → 旧部署的独立更新配对”。首次 writer 令牌使用管理入口：

```bash
docker compose -f docker-compose.example.yml exec javdex node /opt/javdex-manager/index.js bind --config /config/server.json
```

部署侧 writer 恢复将 `bind` 换成 `recover`；不要直接调用镜像内 `/app/index.js`，该目录是首次初始化种子，并不一定是更新后的当前业务版本。

- 在线正式版：检查更新 → 核对目标版本 → 准备在线更新 → 确认停服并安装。由服务端访问 GitHub 正式 Release 和匹配架构的升级文件；不自动追踪或安装预发布。目标正式 Release 尚无单文件升级包时会报错，不能据此认定 0.8.0 具备托管更新能力或 0.9.0 已发布。
- 离线：只选择一个官方 `.javdex-update` 文件，需匹配服务器架构；不是 Docker image archive，也不是只有 JS 的源码包。
- 预发布：显式从对应预发布 Release 下载 `Javdex-server-<version>-linux-amd64.javdex-update` 或对应 arm64 文件。导入仍执行全部签名、版本与迁移检查，不能从正式版降到较低的预发布。安装后桌面也须更新到相同业务版本；历史分离格式不提供兼容入口。
- 续传：重新选择同一升级文件，从持久确认的程序归档偏移继续，不把容器头部和签名 JSON 算入上传偏移。管理进程/容器重启保留偏移；哈希、签名和原生兼容验证通过前不切换程序。
- 完成：桌面版本匹配时自动重连，否则提示同步升级桌面。

下载、上传、解压和原生依赖预检期间原业务继续运行。安装须再次人工确认，会中断所有客户端访问与播放。解除本机更新配对仅删除本机保存的信息；撤销远程设备须使用可信设备列表。已提交的升级由服务端继续执行，撤销发起设备不等于取消升级。旧双端口部署撤销独立更新凭据仍由管理员更换 `/program/state/token` 后重启并重新配对。
