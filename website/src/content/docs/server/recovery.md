流程为 `准备 → 停止业务进程组 → 切换版本 → 迁移并待验证启动 → 持久提交 → 开放业务`。在线升级、上传离线包升级和镜像启动升级均不创建升级备份。

管理器在数据目录持有内核文件锁，并将锁继承给业务子进程，禁止同一资料库同时运行两个托管写入者。停止会转发信号、等待退出、终止超时进程组并确认退出；`init` 负责孤儿回收。业务意外退出使用有限次数的退避重启，计划更新不触发重启竞争，管理器异常退出由 Docker restart 恢复。业务不得启动脱离监督的后台写入进程。

当前任务的 `current.json` 是上传偏移与提交阶段的唯一权威日志；每个任务目录的 `job.json` 只用于清理归档。归档副本写入失败不丢弃已持久上传的数据；权威日志写入失败会回读记录，安装已开始或提交结果无法确认时保留现场。

安装前检查架构、固定运行环境、签名、期限、升级方向、迁移路径、程序暂存空间和资料库身份。客户端入口同时要求升级目标与此客户端版本完全一致。有扫描、未完成备份或需处理的文件维护时阻止升级；停止业务后再次核对维护状态、schema 和资料库身份。升级不遍历、复制或按大小预留整个资料库、图片和已有备份的空间。

新版本迁移后先验证真实查询 worker，期间仅开放健康检查，网页、管理与播放返回维护状态。核对应用/schema/资料库身份后持久提交，再开放业务并核对实际握手。不是只检查 PID 或 running 状态，也不是不停机热更新。

下载、上传和预检失败时原服务继续运行。停止阶段中断且安装尚未开始时，仅在原程序、配置、schema 与资料库身份未改变的条件下重新启动原服务。安装或验证失败、安装中断时，服务保持维护状态，显示“需要人工恢复”，保留现场并拒绝下一次升级；不会用旧程序直接打开可能已迁移的资料库。提交后只继续激活，不自动覆盖可能的新写入。

如有重要资料，建议升级前使用与当前服务端版本一致的客户端，通过[备份与恢复](/Javdex/guide/backup/)手动备份资料库；升级本身不创建、替换或轮换备份。发生需要人工恢复的故障时，请保留数据、程序卷和容器日志，核对故障原因、备份与匹配程序后处理，不手降数据库版本或反复启动旧程序。

成功后保留当前和上一版发行目录，清理已结束且归属管理器的旧任务；不清理独立备份功能创建的文件。未知、损坏或需恢复的记录/目录不自动删除。清理失败显示警告，新业务继续运行，不因此回退数据。
