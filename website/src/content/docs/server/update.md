业务发行包包含入口 JS、真实查询 worker、Web、许可及 Node 原生依赖；CI 在目标 Linux 架构的已验证镜像内形成生产依赖闭包，再生成签名包。升级不在服务器运行 npm install，也不执行上传包的安装脚本。签名绑定版本、构建、平台、运行环境、迁移路径、压缩/展开大小、SHA-256 与期限；目录描述精确覆盖普通文件，拒绝路径越界、链接、重复条目、特殊文件和超额解压。

`.javdex-update` 的运输格式为 8 字节 ASCII `JVDXUPD1`、4 字节大端无符号 JSON 长度、签名 JSON、原始完整 `.tar.gz` 程序归档。清单不超过 65536 字节，不解压额外外层、不从包中建立公钥信任。签名中的大小/SHA-256 绑定内层程序归档，Release 的 SHA256SUMS 绑定整个运输文件。客户端先检查格式、大小和内层摘要，随后由已配对管理器验证签名与升级目标，再上传内层归档；最终摘要、解压闭包和原生校验仍由服务端执行。在线检查仅读取有界文件前缀，在线准备重新验证文件内签名与所选目标一致并流式下载内层归档；旧 JSON 发现和裸归档下载分支已移除。构造运输包后重新读回并核对内层字节，禁止覆盖已有输出文件。

业务版本与容器运行外壳版本不是同一个概念：

- 同一 `node22-bookworm-v1` 内的业务更新，只替换业务目录和子进程，管理入口持续运行。
- 管理器、Node、glibc/OS 维护仍由管理员替换镜像。同一运行环境内，镜像内业务版本高于程序卷当前版本时，启动自动执行安装、验证和提交；版本相同或程序卷更新时保留当前版本，不自动降级。不同运行环境不能直接运行旧发行包，应按对应发布迁移说明操作，不盲目清空程序卷、降 schema 或启动不兼容原生模块。

## 通过镜像升级

将 Compose 的 `JAVDEX_VERSION` 改为目标已发布版本，执行 `docker compose -f docker-compose.example.yml pull` 和 `docker compose -f docker-compose.example.yml up -d`。须保留 `/data`、`/program` 和图片卷；更新会中断业务，升级不会自动备份资料库；如有重要资料，请先使用与当前服务端版本一致的客户端完成备份。“最新业务版本”指本次拉取镜像内的版本，启动不会另行联网寻找或下载业务包。

镜像内容以所选容器镜像为信任来源，并逐文件核对发行描述与摘要、检查原生模块；客户端上传和在线下载的升级文件仍须通过官方签名验证。所有升级入口均不创建升级备份。准备失败时原服务继续运行；安装开始后失败或中断、提交后状态不确定时保持维护状态，保留现场并要求人工恢复，不用旧程序或旧资料自动回退。

同一镜像发行内容只自动尝试一次。空间不足、未完成维护任务或内容验证失败会记录失败，不在容器重启时无限尝试；排除原因后可在客户端显式安装官方升级文件，或采用更新版本镜像。已有上传中或准备好的客户端任务不会被镜像自动升级覆盖。请检查客户端更新状态和容器日志，而不只看镜像标签。

首次创建空程序卷仍按首次部署初始化；若挂接已有旧资料库，须事先人工完整备份，不能将其视为已有托管程序卷的自动升级事务。

管理器代码在镜像内，不跟随业务包自更新。管理进程拥有容器内程序与停启所需权限；业务默认为 1000/1000，可按部署权限设置 `JAVDEX_SERVER_UID/GID`。私有状态目录仅管理进程可访问，发行目录可由业务读取但不可覆盖。同容器两个进程不是安全沙箱。

管理入口必须使用容器内 root，业务 UID 不得为 0。空程序卷的父目录会归属管理进程并限制写权限；已存在却归属业务用户的托管子目录会拒绝接管，请管理员先保留现场、核对权限。不要用 Compose 的 `user: 1000` 改写管理入口身份。

## 运行环境兼容检查

0.8.0 镜像没有托管更新与运行环境查询能力；请先按[首次采用托管更新](/Javdex/server/adoption/)更换 0.9.0 基础镜像，保留数据与图片并增加 `/program` 卷。已发布版本的镜像、标签和升级文件不作覆盖。

客户端将通过统一 HTTPS 地址的 `GET /runtime/v1/info` 查询镜像内管理器的实际运行环境。它只公开环境兼容编号、运行库和架构等粗粒度信息，不要求先配对，不发送设备凭据或业务 AppVersion，也不返回业务版本、目录或资料库身份；HTTPS 证书仍按既有规则校验。业务包不能更新这个镜像环境编号。

当前源码的客户端、镜像及签名升级包要求 `environmentVersion = 1`，必须严格相等。同端口 HTTP／HTTPS 分流由 0.9.0 基础镜像提供，不能只安装业务更新包。因此，即使服务端和客户端的业务版本相同，环境不匹配时仍会显示“服务端升级”卡片。

| 环境检查结果 | 界面与处理 |
|---|---|
| 已确认是 Javdex 服务端，但接口不存在（GET 返回 404／405），或有效环境版本较低 | 显示“需要升级服务端Docker镜像”，禁用在线升级与上传离线包升级 |
| 环境版本相等、运行库兼容 | 继续原有升级检查；业务目标仍须与客户端一致且高于当前服务端，不允许同版本重装或降级 |
| 环境版本较高 | 提示升级客户端，禁用两个升级入口，不建议降级镜像 |
| 未确认的地址返回 404／405，或网络、超时、证书、授权／代理异常、无效响应 | 暂时禁用两个入口，显示无法确认环境及具体原因，可“重新检测”；不据此认定镜像过旧 |

卡片常显“当前环境／本版要求”，保留“查看镜像升级指引”和“重新检测”。在线、离线、准备及安装统一受限，不能通过上传文件绕过；签名清单绑定环境版本，由服务端再次校验。原有签名、期限、架构、schema、完整字节及原生依赖检查继续有效。

### 提示需要升级镜像时

这里要求更新的是 **Javdex 服务端 Docker 镜像**，不是 Docker Engine 软件；客户端不自动执行或强制执行 Docker 操作。

1. 重要资料先使用与当前服务端业务版本一致的客户端，通过现有“备份与恢复”手动备份；升级本身不会生成资料库或图片快照，也不会自动资料回退。
2. 选择与新客户端配套的已发布固定版本镜像，保留原有 `/data`、`/program`、图片卷及部署配置。
3. 拉取镜像后重新创建容器，使新镜像生效。仅拉取镜像或重启旧容器不能完成更换；不要删除数据卷、强制降级或手动降低 schema。跨运行库代际时按对应官方迁移说明操作。
4. 服务恢复后点击“重新检测”；环境相等且业务版本落后时，才继续业务升级。

新管理器先启动 TLS 网关再初始化业务；业务初始化失败时，环境查询仍可达，不可用的业务／更新请求保持 503 维护响应。环境检查不额外阻断状态查看、已提交任务恢复或原本可用的业务。旧已安装发行描述与已提交日志只为启动和恢复读取兼容，不表示接受缺少环境声明、旧格式或未签名的新升级包。安装失败或中断仍须按[人工恢复指引](/Javdex/server/recovery/)处理，不能靠重启自动回退资料。
